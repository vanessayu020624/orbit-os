# OrbitOS

**一个把 CRM 与 ERP 打通、由 Agent 主动发现风险并协同处理的企业运营系统演示。**

虚拟公司「擎源工业设备」是工业传感器 / 伺服电机 / 控制器的 B2B 分销商。销售在承诺交期时看不到库存和在途采购，供应链发现缺货时订单已经签了。OrbitOS 让一个 Agent 横跨客户、商机、订单、库存、采购、应收六个模块自主排查这类跨部门问题，并在需要写数据时停下来请人确认。

## 核心特性

1. **Agent 自主规划，且规划是可见的界面元素。** 采用 Planner–Executor 双层结构：先由 LLM 输出结构化 JSON 计划（`{goal, steps[]}`），Sidekick 立刻把它渲染成带勾选框的清单，然后才开始执行工具。用户在第一秒就知道 Agent 打算干什么，而不是看着工具一个个往外蹦。执行中还可以动态追加步骤（`plan_amended` 事件，清单高亮）。

2. **权限是物理约束，不是提示词里的君子协定。** 四个角色（销售代表 / 销售总监 / 供应链主管 / CEO）对应四套工具集合：`toolsFor(role)` 决定哪些工具会被放进发给 LLM 的 `tools` 数组，`executeTool()` 在执行前再查一次角色。未授权的工具对模型来说不存在，就算它凭幻觉编出工具名也会拿到 `PERMISSION_DENIED`。当前各角色实际可用工具数：销售代表 9 / 销售总监 11 / 供应链主管 10 / CEO 15（共 15 个）。CEO 能用全部工具，包括 4 个写工具，但代做别人职责的写操作会被标注「越权代办」并带 `override: true` 落进审计日志。

3. **写操作强制人工确认（HITL），确认卡写清楚代价。** 4 个写工具在执行前一律暂停，弹出的卡片不是「确认执行吗」，而是「将向【锐驰机电】采购 SKU-203 高精度伺服电机 SV-800 × 48 台，预计成本 ¥591,360，预计到货 2026-09-07（加急）」。用户点「拒绝」后，`{rejected: true, reason}` 会被喂回模型，让它改口给替代方案而不是原地重试。

4. **反编造做在执行期，而不是只做事后标红。** 上线自测时抓到过一次严重故障：销售总监问「本月团队营收和商机漏斗」，执行器**一个工具都没调**，直接输出了 1842.6 万营收、六段漏斗和八个数据库里根本不存在的单号；另一次问「未来两周交付有风险吗」，它跳过两步只读计划，直接拿编出来的 SKU 和数量去调 `create_purchase_order` 下单。这类输出的可怕之处在于它**长得和正确答案一模一样**——用户看到的是一张格式完全正常的确认卡，无从分辨依据真假。

   提示词拦不住它（写了「必须先查再答」照样跳过），`tool_choice: 'auto'` 也拦不住。真正的修法是把它从「模型该不该这么做」变成「模型**能不能**这么做」：还没有任何工具结果时，请求一律带 `tool_choice: 'required'`，模型在这一轮**没有输出正文的选项**，只能调工具；拿到数据后立刻放开，否则它永远没法收尾。这条之上再叠三道兜底守卫（`loop.ts`）：

   - **守卫 A · 零数据不许收尾**——上游万一忽略 `tool_choice`，一段没有任何数据来源的答案也绝不发出去；先追问一次，再不听就中止并让用户重问。
   - **守卫 B · 没查过数据不许写**——既没调过只读工具、计划里也没安排的写操作直接退回，连 HITL 确认卡都不给弹。计划内的写、查完再写都不受影响。
   - **守卫 C · 核不上的引用退回重写**——发出去之前先用 `resolveRef` 逐个核对 `[[编号]]`，把核不上的那几个具体点名喂回模型让它改。只给一次机会：第二次还编，说明它手上确实没有对应数据，标红比无限重试更诚实。

   还有一类不编单号、改编「为什么查不到」的幻觉（「2025 年订单已归档至总部财务系统」——系统里没有归档这回事），三道守卫都拦不住，靠提示词硬约束：工具只告诉你查不到、有多少条不可见，**从不解释原因**，所以原因你并不知道，不许补一个听起来合理的机制。

   修完做了 12 条预置问题 + 2 条边界问题的真实模型端到端回归，逐条核对结论里每个编号能否在数据库中查到：**14/14 场景 + 1 条多轮追问链全部通过，结论里 95 条 `[[编号]]` 引用无一核不上**（引用条数每次跑不同，模型是非确定性的；恒定的是「核不上 0 条」这个判据）。

5. **数字溯源 / 空结果显式化。** 结论里的每个记录号都用 `[[SO-2026-0428]]` 标注，前端渲染成可点击 chip，点一下带着关键词跳到对应页面并自动定位到那一行；核不上的引用会被标红划掉，而不是伪装成正常 chip。工具查不到数据时返回 `{found: false, reason}` 而不是空数组，逼模型说「未找到」而不是拿别的数据顶上。

   模型写回来的是 Markdown（15 条真实结论里有 23 处加粗、67 行列表、15 行小标题），所以结论区做了一个极简渲染层。这里有个必须踩对的顺序：**先按 `[[编号]]` 切段，再对非引用段做 Markdown**——反过来的话 `**[[AR-002]]**` 会先在星号处断开，引用被劈成两半、chip 不成立，整条溯源链就废了。这条顺序单独抽成纯函数 `splitInline()` 钉在单测里。不引 `react-markdown`：它为完整 CommonMark 带进 30KB+，而模型实际只用到五种语法。

   更根本的一道防线在数据口径上：工具返回给模型的每个标识符，都必须是界面上真实显示、用户搜得到的业务单号。数据层每条记录有两套标识——内部主键（`SO-001`）与业务单号（`SO-2026-0412`）——把整条记录原样喂给模型，它会引用前者，用户在任何页面都搜不到，看起来就是编的。`agent/present.ts` 做投影，`present.test.ts` 用 `resolveRef` 把这条不变量钉死：**模型能看到的每个标识符，用户都能在界面上核到**。

6. **多轮上下文有上限，且这个上限是摆给用户看的。** 追问链要能接得住（「第三条那个客户」「就按方案 1 来」），所以最近 6 轮问答原样进提示词；再往前的轮次异步折叠成一段不超过 300 字的摘要，摘要和原文在提示词里**分两段呈现**——摘要是二手转述，模型需要知道哪部分能逐字引用、哪部分只能当背景（提示词里明说「不要从摘要里摘编号当数据来源」，那正是引用核不上的来源之一）。摘要走一次额外的模型往返，所以是 fire-and-forget：不让用户为它多等一秒，它失败也不影响这一轮的结果已经记下来。

   Sidekick 底部的「上下文」面板把这套机制直接摊开给用户：原样带了几轮、更早的摘要写了什么、上次实际发出多少输入 token、以及「切换角色会开一条属于新角色的会话，上下文不跨角色带过去」。Agent 产品最常见的信任崩塌是用户以为它记得、实际上它早忘了——**把记忆边界画在界面上，比把它藏在代码里诚实**。

7. **Agent 干预的结果当场反映在看板上。** 批准采购单后 store 真的落库，仪表盘的「交期风险订单」KPI 从 2 变 0，红色风险卡消失。屏幕上任何数字变化都只可能来自 Agent 的写操作，且能在审计日志里对上——没有任何模拟的定时跳动。

8. **失败就是失败，但失败要给出路。** LLM 超时 / 限流 / 断网 / 服务端报错分类成四种用户能据此行动的说法（`describeLlmError`），配一个可直接点的「重新问一次」，并指明左侧业务数据不依赖模型。早期版本在这里做过「录播模式」——预置事件流回放，除一个小角标外与真实执行毫无差别——已彻底删除：一段看不出真假的演示，只要被追问一次「这是真跑的吗」，全部可信度就没了。

9. **结论能走出系统，也能从系统外面被问出来。** 飞书这条链路做了两层，两层的取舍完全不同。

   *单向*：风险卡上有个「推送到飞书」，`/api/notify` 把它拼成交互式卡片发到群机器人 webhook。做这件事的产品理由是 B 端负责人一天不会主动打开三次控制台，**Agent 发现的问题必须去找人，而不是等人来找它**。两个细节：卡片正文一律 `plain_text` 不用 `lark_md`，因为 detail 里带着单号和金额，出现 `*` 或 `[` 会被飞书当格式吃掉；飞书对失败的推送照样回 HTTP 200，真正的结果在 body 的 `code` 里，只看 `upstream.ok` 会把签名错误当成推送成功——**静默成功比报错危险得多**，未配置 webhook 时这里是明确的 400，不是一个假的「已推送」。

   *双向*：群里 @星轨 直接问，`/api/feishu/events` 收到事件后在 Cloudflare Worker 里跑**同一份执行器**（`loop.ts` 一行没改——它本来就把环境相关的东西全收在 `RunAgentOptions` 里，服务端只是换一组实现注进去），答案作为卡片回到原消息下面。这一层真正难的不是协议，是**把权限、人工确认、溯源这三件事在系统外面重新建立起来**：

   - **权限不由飞书决定。** 飞书只给一个 `open_id`，映射成哪个 OrbitOS 用户由 `FEISHU_USER_MAP` 说了算，映射不到的人问什么都不回答（卡片会把 `open_id` 原样打出来，方便管理员照着配）。不给「默认只读身份」这个台阶：在一个演示 CRM 里放行陌生人，和在真实系统里放行是同一个动作。
   - **写操作在飞书这一侧永远拿不到批准。** 服务端注入的 `requestConfirm` 恒返回 `false`，而 `loop.ts` 里每个 `isWrite` 工具都必经这一关——所以这是结构上的拦截，不是约定。被拦之后 Agent 会继续推理并给出建议，用户在飞书里拿得到「该做什么」，拿不到「已经做了」；卡片上给的是一个带 `?role=&ask=` 的回跳链接，人点回网页、在能看见完整上下文和审计留痕的地方按确认。
   - **一次工具都没调的结论直接拦下。** 浏览器里有守卫 A 兜这件事，飞书这侧照样要兜——**发到群里的消息比屏幕上的更难撤回**。

   还有两个必须讲清的工程约束：飞书要求 **3 秒内返回 200**，否则判定失败并最多重推 3 次（表现是同一个问题被回答三遍），而一次问询要跑 6~40 秒，所以这里收到就 ACK、执行丢进 `waitUntil`；事件去重用的是实例内存，**换隔离实例就失效**，它挡的是同实例上几秒内的重推，不是严格幂等——真要做得上 KV/D1，那是这个演示项目里不成比例的复杂度。这两条都写在代码注释里，是边界不是遗漏。

10. **歧义先消解，再执行——最多问一次。** 自然语言里最危险的不是「问得难」，是「问得像是很清楚」。「最近这批订单交期有风险吗」——「最近」是 7 天还是 30 天？「公司最大的客户是谁」——按累计成交、按未结应收、还是按客户体量？这三种口径给出的是三个不同的名字，而模型会**直接挑一个然后自信地答**，用户看不出它挑了哪个。

    所以在规划之前加了一道闸：判定为歧义就停下来，给出可点的口径选项，用户点了才往下走（`clarify.ts` + `ClarifyCard`）。三条产品约束是结构性保证的，不是靠提示词求来的：

    - **只在「换个理解会查到完全不同的一批数据」时拦。** 拦得太勤比不拦更烦人——一个每次都反问一遍的助手，用户第三次就不用了。所以有一组回归测试专门钉这件事：全部内置预置问题与全部风险卡问题，逐条断言**不会被误拦**（唯一的例外是 CEO 那条「公司最大的客户是谁？」，它是刻意留着当演示素材的）。
    - **最多一轮。** 第二轮无论如何往下走。来回澄清三次的 Agent，不如一个说清楚假设的 Agent。
    - **兜底口径是必填字段，不是可选补充。** 没有它，澄清闸就退化成一个能把对话卡死的模态框。用户跳过、或飞书那条链路上根本没有「点一下」这个动作时，一律走兜底并**把用过的口径印在结论里**（网页上是卡片，飞书上是卡片脚注的一行小字）。

    实现上有个刻意的成本决策：语义判定**搭规划器的顺风车**（`Plan` JSON 里多一个 `clarify` 字段），而不是单开一个「歧义分类器」调用——后者会让**每一个问题**都多付一次模型往返。更前面还有一层确定性规则预检（悬空指代 / 多实体重名 / 模糊时间 / 最高级形容词），命中时零模型开销。只有真正触发澄清才多付一次重新规划。

11. **手机上是另一个产品形态，不是桌面版的窄版本。** 桌面工作台的核心动作要三栏同屏（读结论 ↔ 点结论里的编号 ↔ 回数据区核对），折成单栏之后这个动作物理上就不存在了。所以这里没有做响应式收缩，而是按宽度分发两套外壳（`viewport.ts` 的 `pickShell`）：

    - **< 768px 走移动版**（`src/mobile/`）。首屏就是星轨对话 + 主动风险卡——手机上用这个系统的场景本来就是「路上被问一句、要一个结论」，翻六张报表那件事发生在工位上。结论里的 `[[编号]]` 点开不再是跳页面，而是**从底部推上来一张记录卡**，关掉就回到对话原位、一个字没动；记录卡上的关联编号可以继续点，形成一条可回退的核对链。桌面的六张数据表压成卡片流，每条只留四个位置（编号 / 归属 / 状态 / 一个最该看的数字）。
    - **768~1023px 保留原来那张说明卡**：桌面三栏在这个宽度必破版，移动外壳在这个宽度又空得不像话。卡上实时显示当前窗口宽度，另给一个「仍要继续」的放行开关，不把人锁在外面。

    两套外壳共用同一份数据、同一套权限（`scope*` / `mask*`）和**同一批对话卡片组件**——确认卡、澄清卡、溯源 chip 在手机上和桌面上是同一个组件，不是简化版。移动端的字段挑选与卡片口径抽成纯函数（`dataCards.ts` / `recordLookup.ts`）单独测，其中一组测试专门钉「手机上不能比桌面多看到一条、也不能少脱敏一个字段」。

## 本地运行

```bash
npm install
npm run dev          # http://localhost:5173
```

⚠️ **`npm run dev` 不会启动 Pages Function，`/api/chat` 会返回 404**，Sidekick 会给出「连不上模型服务」的失败卡（业务页面不受影响，仍可正常浏览）。要在本地跑真实 LLM：

```bash
# 需要一个阿里云百炼 API Key（bailian.console.aliyun.com 开通 DashScope 后获取）
npx wrangler pages dev -- npm run dev
# 或先构建再起：
npm run build && npx wrangler pages dev dist --binding DASHSCOPE_API_KEY=<your-key>
```

其他命令：

```bash
npm test             # vitest run，应为 24 files / 392 tests 全绿
npm run build        # tsc -b && vite build
npm run lint         # oxlint
```

**端到端回归**（打真实模型，不进 `npm test`）：

```bash
# 12 条预置问题 + 2 条边界问题各跑一遍完整链路，逐条核对结论里每个 [[编号]] 能否在库里查到
E2E_OUT=/tmp/e2e.md npx vitest run --config vitest.e2e.config.ts
E2E_ONLY=sc-1,ceo-2 E2E_OUT=/tmp/e2e.md npx vitest run --config vitest.e2e.config.ts   # 只跑指定场景
```

它打的是线上 `https://orbit-os.pages.dev/api/chat`，需要外网、跑一遍约 4～5 分钟。
**改提示词或改 `agent/loop.ts` 之后必须跑一遍**——这两处的回归单元测试测不出来，
只有真模型会告诉你它又开始编了。当前基线：**15/15 通过（14 场景 + 1 条追问链），0 条引用核不上**。

## 部署说明

托管在 **Cloudflare Pages**（而非 Vercel：`vercel.app` 在国内 DNS 污染严重，面试现场打不开就是事故；`pages.dev` 国内可达性明显更好）。

1. 推送到 GitHub，在 Cloudflare Pages 里连接该仓库。
2. 构建配置：构建命令 `npm run build`，输出目录 `dist`。
3. 在 Pages 项目的 **Settings → Environment variables** 里加 `DASHSCOPE_API_KEY`，值为阿里云百炼的 API Key。
4. `functions/api/chat.ts` 会被自动映射为 `/api/chat`，它读取该环境变量并把请求原样转发给 `https://dashscope.aliyuncs.com/compatible-mode/v1/chat/completions`。
5. 想启用**飞书推送**（单向），加两个环境变量：`FEISHU_WEBHOOK_URL`（群设置 → 群机器人 → 添加自定义机器人后拿到的地址）和可选的 `FEISHU_WEBHOOK_SECRET`（机器人开启「签名校验」时才需要，`/api/notify` 会按 `timestamp + "\n" + secret` 作 HMAC-SHA256 密钥算签名）。**不配也不影响其余功能**：`/api/notify` 会返回 400 `NO_WEBHOOK` 并在界面上直说「推送功能在当前部署上未启用」，不会假装发成功。

6. 想启用**群里 @星轨 直接问**（双向），需要一个企业自建应用（要企业管理员权限）：

   1. [开放平台](https://open.feishu.cn/app) → 创建企业自建应用 → 「添加应用能力」里加**机器人**。
   2. 「权限管理」申请：`im:message`、`im:message.group_at_msg`（群里 @ 才收得到）、`im:message:send_as_bot`。
   3. 「事件订阅」→ 请求地址填 `https://<你的域名>/api/feishu/events`，订阅 `im.message.receive_v1`。**建议同时设置 Encrypt Key**：配了才有请求验签，不配就只能比对 Verification Token。
   4. 「版本管理与发布」创建版本并提交，**等管理员审核通过**——这一步不做，机器人加不进群。
   5. 在 Pages 环境变量里加：`FEISHU_APP_ID`、`FEISHU_APP_SECRET`、`FEISHU_ENCRYPT_KEY`、`FEISHU_VERIFICATION_TOKEN`、`FEISHU_USER_MAP`（形如 `{"ou_xxx":"U-006"}`，把每个人的 `open_id` 映射到 OrbitOS 用户 id）。
   6. **重新部署一次**。Cloudflare 的环境变量只对新部署生效，改完不重新部署等于没改——这一步最容易被跳过。
   7. 把机器人拉进群，@它问一句。第一次问的人如果还没在 `FEISHU_USER_MAP` 里，机器人会回一张卡片，上面就写着他的 `open_id`，照着补进去即可。

   本地调这条链路：`.dev.vars` 里配好上面这些（`.env.local` 对 Pages Function 无效），`npm run build && npx wrangler pages dev dist`，再用任意公网隧道把本地端口暴露出去，把隧道地址填进事件订阅的请求地址。

**API Key 不进前端产物。** 浏览器只请求同源的 `/api/chat`，Key 只存在于 Cloudflare 的环境变量里。未配置 Key 时该 Function 返回 503 `NO_KEY`，前端捕获后走预置演示兜底而不是白屏。

`public/_redirects` 里配了 SPA 回退，否则在 Pages 上直接刷新 `/orders` 这类子路由会 404。
