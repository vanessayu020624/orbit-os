# OrbitOS Agent 设计说明

> 这份文档回答的不是「我做了什么」，而是**「为什么这么选，代价是什么，什么情况下我会选另一个」**。
> 所有事实性描述以仓库代码为准（`src/agent/`、`src/lib/`）；所有尚未实测的性能与成本数字一律标注「**待实测**」并附测量方法——本项目开发环境无外网，这些数据只能在联网环境跑真实 GLM 调用才能得到，我不填看起来合理的估算值。

**当前实现的骨架**

```
提问
 └─ ① Planner    LLM 一次 JSON 调用 → {goal, steps[], needsWrite}   loop.ts:27-42
 └─ ② Executor   function calling 循环，MAX_TURNS = 12              loop.ts:58-125
      ├─ 每轮：正文正则匹配「需要追加步骤：」→ 动态追加步骤          loop.ts:69-77
      ├─ 每个 tool_call：写工具 → HITL 拦截 → 批准才 executeTool     loop.ts:99-115
      └─ 某轮无 tool_calls → 收尾，抽取 [[记录号]] → final           loop.ts:79-88
```

工具 15 个（只读 11 / 写 4），角色 4 个，各角色实际可用工具数：销售代表 9、销售总监 11、供应链主管 8、CEO 11。模型是智谱 **GLM-4.5-Flash**，`temperature 0.2`，经 Cloudflare Pages Function 代理（`functions/api/chat.ts`），API Key 只存在于 Cloudflare 环境变量。

## 1. 为什么选 Planner–Executor 而不是纯 ReAct

### 结论先行

纯 ReAct 的规划是**隐式**的：它藏在每一轮「思考 → 调工具 → 观察」的内部推理里，用户从外面看只能看到工具一个接一个地蹦出来，直到某一轮它突然停下来给结论。这在技术上没问题，在产品上有两个致命缺陷：

1. **用户无法预期。** 用户看到第 1 个工具跑完，不知道后面还有 1 个还是 8 个，不知道这次要花 3 秒还是 40 秒。一个不知道自己要等多久的等待，主观上比实际时长更长。
2. **用户无法中断。** 想打断得先知道它跑错了方向，而在纯 ReAct 里，「方向」这个东西根本没有被表达出来——等你看出来跑偏了，钱已经烧完了。

Planner–Executor 把规划从模型的内部推理里**拽出来变成一个界面元素**：`loop.ts` 第一阶段用 `jsonMode` 强制 LLM 输出 `{goal, steps[]}`，Sidekick 立刻把它渲染成带勾选框的清单。用户在任何工具执行之前就看到了「Agent 打算干这 4 件事」。

对一个要给人看的 Agent 产品来说，**「让规划可见」本身就是功能**，不是技术副产品。

### 代价

- **多一轮 LLM 调用**，而且这一轮阻塞在所有工具执行之前——它加的是首字延迟（TTFT 意义上的「第一个界面元素出现」前的等待），是用户感知最敏感的那一段。
- **计划可能失真。** Planner 只看到工具的名字和描述（`toolCatalogText(role)`），看不到任何真实数据，所以它列的步骤是「基于常识的猜测」。真实执行完全可能偏离计划——这就是为什么必须做 `plan_amended` 动态追加，否则清单会和实际执行对不上，反而毁掉可信度。
- **进度映射是近似的。** 这一点必须诚实说明：`loop.ts` 的 `stepIdx` 是**每轮循环推进一格**（`loop.ts:118-124`），而不是根据「这一轮实际调用的工具是否等于该步骤的 `expectedTools`」来判定。一轮里调了三个工具、或者一个步骤跨了两轮，勾选进度就会和真实执行错位。这是我为了 P3 的工期做的简化。要修的话，正确做法是拿 `expectedTools` 与本轮 `tool_calls` 求交集来推进步骤，代价是模型不按计划调工具时步骤会卡住不动，需要额外的兜底规则——**这是个真实的取舍，不是遗漏**。

### 实测数据（待补）

| 指标 | 实测值 | 测量方法 |
|---|---|---|
| Planner 调用额外延迟 | **待实测** | 在 `loop.ts:27` 的 `chat()` 调用前后 `performance.now()` 打点，剧本 A 连跑 10 次取中位数与 P90 |
| 首个界面元素出现耗时（Planner 方案） | **待实测** | 从 `ask()` 进入到 `emit({type:'plan'})` 的墙钟时间，10 次中位数 |
| 首个界面元素出现耗时（纯 ReAct 对照） | **待实测** | 临时跳过 Planner 阶段直接进 Executor，测到第一个 `tool_call` 事件的时间，同样 10 次 |
| Planner 输出 JSON 解析失败率 | **待实测** | 统计 `extractJson()` 抛异常的次数 ÷ 总调用数（`llm.ts:46` 已为 GLM 偶尔套 markdown 围栏做了兜底，需要知道这个兜底被触发的频率） |

上表第二、三行的**差值**才是这个设计的真实代价，单独看第一行会高估——因为纯 ReAct 的第一轮调用同样要等模型输出，只是输出的是 tool_call 而不是计划。

### 什么情况下我会选纯 ReAct

- **任务是单跳查询**（「SKU-203 还有多少库存」）。多一轮规划纯属浪费，规划的价值随任务步数增长，一步的任务价值为零。
- **延迟是硬约束**的嵌入式场景（比如在输入框里做实时建议），几百毫秒的额外等待比「过程不透明」严重得多。
- **没有可展示的界面**（纯 API 输出、CLI、语音）。Planner 的收益几乎全部兑现在视觉呈现上，没有屏幕就不值这一轮钱。

反过来，如果任务步数继续涨（>8 步）、或者步骤之间有真实依赖需要回溯，我会往 **Plan-and-Execute + Replan** 走：每执行 N 步回到 Planner 重新审视剩余计划。现在的实现只有「追加」没有「重排/删除」，`plan_amended` 事件只支持 `addedSteps`（`types.ts` 的事件契约），这是当前架构的天花板。

## 2. 工具边界怎么切

### 三条原则

**① 一个工具对应一个业务问题，不做万能查询接口。**

最偷懒的做法是给 LLM 一个 `query(entity, filter)` 甚至 `run_sql(sql)`。它省事，但会同时毁掉四件事：

- **权限没法声明。** 现在每个工具上写着 `allowedRoles: ['supply_chain', 'ceo']`，权限是工具的静态属性，可以被测试、被审计、被 diff。换成万能接口，权限就得下沉到查询解析里去做——那是个 SQL 注入级别的攻防问题，而不是一个配置。
- **脱敏没法做。** `maskOrderForRole()` 之所以能生效，是因为「订单查询」这个操作有明确的返回形状。万能接口返回什么字段由模型的查询决定，脱敏无从下手。
- **调用准确率下降。** 工具描述是 LLM 唯一的说明书。`get_supplier_options: 查询某 SKU 的可选供应商，含交期、准时率、价格系数与预估单位成本，按交期升序排列` 这句话本身就在告诉模型「什么时候该用我」。一个 `query()` 的描述必然是抽象的，模型只能靠自己猜数据模型长什么样。
- **审计没有语义。** `auditOf()` 记的是工具名+入参，「王强调用了 create_purchase_order」是一条有业务含义的审计；「王强执行了一条 SQL」不是。

**② 确定性计算不交给 LLM，LLM 只决定何时调用。**

`simulate_delivery_risk` 背后是 `src/lib/risk.ts` 里 40 行纯函数，做的是库存扣减、日期差、风险分级。这类计算交给 LLM 是把稳定的东西换成不稳定的——同一份数据，代码永远算出 48，模型有一定概率算出 50 或 42，而你没有办法在事后知道它这次算对了没有。工具描述里那句「**这是本地确定性计算，不是估算**」是写给模型看的，让它别自作聪明地重算或修正。

**③ 粒度：过细则轮数暴涨，过粗则无法组合。**

过细的例子是「一次只查一个 SKU 的库存」。`check_inventory` 的参数刻意是 `skus: string[]` 数组而不是单个 `sku`——一张订单最多 3 个行项目，7 张待发货订单最坏要查 21 次；数组版一次搞定。Executor 的 `MAX_TURNS = 12`，粒度切太细的工具会在真实任务上直接把预算撞穿。

过粗的例子是把「排查交期风险 + 比选供应商 + 下采购单」做成一个 `handle_delivery_risk()`。那 Agent 就退化成一个按钮：它无法只排查不下单，无法在比选之后停下来问人，HITL 也没地方插——因为写操作被埋在一个复合工具内部了。**工具的粒度上限，就是人能介入的最小粒度。**

判定标准我用一句话概括：**一个工具应该对应一次「人也会这样做」的操作**。供应链主管会「查一批 SKU 的库存」，不会「查第 1 个 SKU 的库存」；他会「比一下供应商」，不会「比完供应商顺便下单」。

### 反例详解：为什么 `simulate_delivery_risk` 不能拆成三个工具

拆开的话，最自然的拆法是：

```
query_pending_orders(withinDays)  →  check_inventory(skus)  →  (LLM 自己做减法)
```

看起来完全可行，而且每个工具都更「原子」。但对着 `risk.ts:21-59` 的实现看一眼就知道它错在哪：

```ts
const ledger = new Map(db.inventory.map(i => [i.skuId, i.available]))
const orders = orderIds.map(...).sort((a, b) => a.promisedDeliveryDate.localeCompare(b.promisedDeliveryDate))
for (const line of o.items) {
  const avail = ledger.get(line.skuId) ?? 0
  const gap = Math.max(0, line.qty - avail)
  ledger.set(line.skuId, Math.max(0, avail - line.qty))   // ← 关键：账本被扣减了
  ...
}
```

**这不是三次独立的比较，是一次带状态的顺序分配。** 订单先按承诺交期升序排（先到期的先占库存），然后共用同一个 `ledger` 逐笔扣减。

代入真实数据（`generateSeed(42)`，SKU-203 可用 42 台）：

| 订单 | 交期 | 需求 | 扣减前可用 | 缺口 | 扣减后 |
|---|---|---|---|---|---|
| SO-2026-0412（华宁自动化） | 2026-09-08 | 40 | 42 | **0** | 2 |
| SO-2026-0428（中科机电） | 2026-09-10 | 30 | 2 | **28** | 0 |
| SO-2026-0435（长风精工） | 2026-09-11 | 20 | 0 | **20** | 0 |
| | | 合计 90 | | **合计 48** | |

现在看拆开之后 LLM 会怎么算。它拿到的是「可用 42」这一个数和三张订单的需求数 40 / 30 / 20，最自然的推理是**逐单比较**：

- 40 ≤ 42 → 没问题
- 30 ≤ 42 → 没问题
- 20 ≤ 42 → 没问题
- **结论：三张订单都没有风险。**

这个答案不是「不够精确」，是**方向性错误**——它会让供应链主管什么都不做，然后在 9 月 10 日被中科机电打电话催货。而且它错得非常隐蔽：每一步的比较都是对的，工具返回的数据也全都是真的，错的是「库存不能被重复分配」这条业务规则。**这条规则不在任何一个工具的返回值里，只在人的脑子里和 `risk.ts` 的代码里。** 指望 LLM 在没有被明确告知的情况下自己想到它，是把业务正确性押在模型的推理运气上。

除了这个核心错误，拆开还要付：

- **轮数**：从 1 轮变成至少 3 轮（查订单 → 查库存 → 查在途采购单），加上模型的中间推理输出，`MAX_TURNS = 12` 的预算被吃掉四分之一。
- **中间态污染上下文**：`query_pending_orders` 返回 7 张订单的完整 JSON，`check_inventory` 返回若干 SKU 的完整 JSON，这些原文都会被 `messages.push()` 进对话历史（`loop.ts:115`）并在后续每一轮重复发送。合并成一个工具，只有最终的 `risks` 数组进上下文。
- **`incomingEta` 这条链会断**：风险等级依赖「该 SKU 最早的在途/已下单采购单 ETA」与承诺交期的日期差（`risk.ts:39-53`）。拆开之后 LLM 要自己筛 `status === '在途' || '已下单'`、自己匹配 `skuId`、自己取最小 ETA、自己算日期差、自己分级。这是五个可以各自出错的环节，每一个都是「看起来算对了」的那种错。

所以边界画在这里：**LLM 决定「现在要不要测算交期风险、测算哪些订单」，代码决定「怎么算」。** 前者是判断，后者是规则。判断交给模型，规则交给代码。

## 3. 权限为什么放在工具层

### 三种做法的对比

| 做法 | 能挡住谁 | 挡不住谁 |
|---|---|---|
| **UI 隐藏**（不给按钮） | 手点的用户 | Agent。LLM 直接调工具，根本不经过界面 |
| **Prompt 约束**（「你不能查全公司数据」） | 听话的模型 | 不听话的模型、被诱导的模型、以及**没有恶意只是搞混了的模型** |
| **工具层拦截** | 全部 | —— |

第二行值得多说一句：讨论 prompt 约束时人们总想到「越狱攻击」，但在企业内部系统里更常见、也更危险的是**无意越权**——模型没有被攻击，它只是在回答「公司最大客户是谁」时诚实地想调一个聚合工具。Prompt 是概率性的软约束，而权限必须是二值的。**一个有 3% 概率失效的权限系统，等于没有权限系统。**

### 实现：两层 + 数据层

**第一层 · 工具可见性**（`registry.ts:10-12`）

```ts
export function toolsFor(role: Role): ToolDef[] {
  return ALL_TOOLS.filter(t => t.allowedRoles.includes(role))
}
```

`toolSchemasFor(role)` 的结果就是发给 LLM 的 `tools` 数组，`toolCatalogText(role)` 的结果直接嵌进 Planner 的 system prompt。对销售代表张伟来说，`aggregate_metrics` **在他的世界里不存在**——不是「不让用」，是没听说过。这一层同时解决了信息泄露：工具列表本身就是能力清单，让低权限角色看到「有一个全公司聚合工具但你不能用」是没必要的。

**第二层 · 执行前复查**（`registry.ts:28-40`）

```ts
export function executeTool(name: string, args: any, ctx: ToolContext): ExecResult {
  const tool = ALL_TOOLS.find(t => t.name === name)
  if (!tool) return { ok: false, ms: 0, result: { error: `不存在名为 ${name} 的工具` } }
  if (!tool.allowedRoles.includes(ctx.role)) {
    return { ok: false, ms: 0, result: {
      error: 'PERMISSION_DENIED',
      reason: `当前角色无权调用 ${name}`,
      allowedRoles: tool.allowedRoles,
    } }
  }
  ...
}
```

为什么第一层已经过滤了还要第二层？因为**模型会幻觉出工具名**。它在预训练里见过无数 CRM 系统，完全可能凭空调用一个 `get_company_revenue`；或者在多轮对话中角色被切换后，沿用上一轮上下文里的工具名。第一层管的是「发出去的能力清单」，第二层管的是「进来的调用请求」——**入口和出口都要查，这是最基本的防御性编程**。

这一层被测试直接钉住（`src/agent/registry.test.ts:42-51`）：

```ts
describe('权限第二层：执行拦截', () => {
  it('绕过工具列表直接调用也会被拒', () => {
    const r = executeTool('aggregate_metrics', { metric: 'top_customers' }, ctxFor('张伟'))
    expect(r.ok).toBe(false)
    expect((r.result as any).error).toBe('PERMISSION_DENIED')
  })
  it('不存在的工具名返回错误而非抛异常', () => {
    expect(executeTool('drop_database', {}, ctxFor('陈立')).ok).toBe(false)
  })
})
```

第一条测试完全绕过了 `toolsFor()`，模拟的正是「模型凭空调用一个它拿不到的工具」。第二条同样重要但容易被忽略：**未知工具名必须返回结构化错误，不能抛异常**——抛异常会让整个 Executor 循环崩掉，一个模型的幻觉就能让会话终止。

**第三层 · 数据作用域**（`rbac.ts` + 每个工具的 `run` 内部）

工具可达 ≠ 数据可见。`scopeCustomers` / `scopeOrders` / `scopeOpportunities` 按 `ownerId` / `teamId` 裁剪记录集，`maskOrderForRole` 把供应链主管看到的 `totalAmount` 与 `unitPrice` 替换成 `***`。

这一层有一个真实踩过的坑，值得单独讲，因为它是「权限漏洞长什么样」的绝佳标本：`simulate_delivery_risk` 对**所有四个角色**开放，前两层都放行。但它接受一个 `orderNos` 参数——如果直接按订单号查库，销售代表就能通过传入别人的订单号读到不属于自己的数据。**工具级权限通过了，数据级权限被绕过了。** 修法是在 `analytics.ts:100-111` 里对传入的订单号先过一遍 `scopeOrders`，越权的被过滤而不是静默混入结果，并且把被过滤的数量显式回报给模型：

```ts
const scopedRefs = new Set(scoped.flatMap(o => [o.id, o.orderNo]))
const allowed = requested.filter(x => scopedRefs.has(x))
deniedCount = requested.length - allowed.length
```

对应两条测试（`registry.test.ts:79-98`）：全部越权时返回 `{found: false}`，混合传入时只返回合法订单并带 `deniedCount: 1`。**混合场景那条比全越权那条更重要**——静默丢弃越权数据而不告诉模型，模型会以为它拿到了完整答案，然后基于残缺数据给出自信的结论。

### 代价与边界

- **多了一次遍历。** `ALL_TOOLS.find()` 是 15 个元素的线性查找，成本可以忽略；真实系统里 `allowedRoles` 会换成策略引擎，那时要考虑缓存。
- **权限逻辑分散在 15 个工具的 `run` 里。** 第三层没有统一的中间件，每个工具自己调 `scope*`。好处是显式、易读、每个工具能表达自己的特殊规则（比如 `check_inventory` 库存数据对全角色开放，不需要 scope）；坏处是**新增工具时可能忘记调用**。如果工具数涨到 50+，我会把 scope 提升为 `ToolDef` 上的声明式字段（`scope: 'own' | 'team' | 'all'`），由 `executeTool` 统一施加——现在不做是因为 15 个工具的规则差异太大，过早抽象会得到一个到处是例外的中间件。
- **必须说明的边界：这个演示里三层全在浏览器端。** 前端权限拦截防的是模型，不是防用户——用户打开 devtools 就能改 `currentUser.role`。生产环境里工具注册表和 `executeTool` 必须跑在服务端，前端只发问题、收事件流。**架构不用变**（`toolsFor` / `executeTool` 是角色的纯函数，搬到哪都成立），**要变的是信任边界的位置**。这一点我在演示时会主动说，因为它是这套设计最容易被追问的地方。

## 4. 幻觉防护三道防线

三道防线各自拦截一类幻觉，互不替代。

### 防线一 · 数字溯源 —— 拦「编造数字」

**这类幻觉长什么样**：Agent 说「SKU-203 目前库存约 50 台，缺口大约 40 台」。数字量级对、听起来专业、完全是编的。它最危险的地方在于**看起来比正确答案更像正确答案**——真实答案往往是 42 这种不圆整的数。

**怎么拦**：Executor 的 system prompt 前两条是硬约束（`prompts.ts:40-42`）：

```
1. 【禁止编造】回答中出现的每一个数字、单号、客户名、日期，都必须来自工具返回结果。
   绝不估算、推测或凭常识填充。宁可说"数据不足"也不要编。
2. 【必须溯源】结论中引用具体记录时用双方括号标注，例如 [[SO-2026-0412]]、[[SKU-203]]、[[PO-2026-0117]]。
```

`loop.ts:85` 用正则 `/\[\[([^\]]+)\]\]/g` 抽出所有标记，`RefChip.tsx` 的 `renderWithRefs()` 把它们渲染成可点击的蓝色 chip，按前缀路由到对应列表页（`SO-` → `/orders`，`SKU-` → `/inventory`，`PO-` → `/purchases`…）。

**为什么这个设计有用**：它把「验证成本」压到了一次点击。面试官或用户不需要相信 Agent，点一下 chip 就能看到原始记录。**可验证性比准确性更重要**——一个 95% 准确但无法验证的系统，和一个 90% 准确但每条都能一键核对的系统，后者在企业里能用，前者不能。

**这道防线的漏洞（诚实交代）**：正则只负责渲染标记，**不负责校验标记指向的记录是否真实存在**。模型完全可以编一个 `[[SO-2026-9999]]` 出来，chip 照样渲染，点进去是订单列表页，用户不一定当场发现。补法很明确、也很便宜——把本次会话所有 `tool_result` 里出现过的 ID 收进一个 Set，`final` 事件里的 refs 逐个比对，对不上的 chip 渲染成黄色警示（原设计文档里写了「无法溯源的数字在 UI 上标黄」，实现时没做到）。**这是当前实现与设计意图之间最大的一处缺口，我不会在演示里假装它已经做了。**

### 防线二 · 写操作 HITL —— 拦「越权行动」

**这类幻觉长什么样**：Agent 的分析全对，但行动错了——把 48 台写成 480 台，把供应商选成了没有该 SKU 供应能力的那家，或者在用户只是问「有没有风险」的时候直接把采购单下了。这一类的特点是**不可逆**：查错了刷新一下就好，写错了要走退单流程。

**怎么拦**：`loop.ts:99-110` 在每个 tool_call 执行前检查 `def?.isWrite`，命中就把执行挂起在一个 Promise 上，等 UI 返回用户的决定。4 个写工具（`create_purchase_order` / `update_order_promise_date` / `reserve_inventory` / `create_followup_task`）无一例外。测试 `CEO 拿不到任何写工具` 与 `共 15 个工具，其中 4 个写工具` 把这个集合钉死，新增写工具时如果忘了声明 `isWrite: true`，测试会红。

详细的产品设计见 §5。

### 防线三 · 空结果显式化 —— 拦「无中生有」

**这类幻觉长什么样**：这是三类里最阴险的。用户问「查一下明远智造这个客户」，而这个客户不在他权限范围内。工具返回空数组 `[]`，模型看到空数组，倾向于两件事之一：用另一个客户的数据顶上（「明远智造年采购额约 200 万」——那是它从别的记录里顺手拿的），或者自己编一段合理的说辞。**空数组对模型来说是一个没有信息量的信号**，它会用先验知识去填这个真空。

**怎么拦**：工具查无数据时**绝不返回空数组，返回带原因的对象**。真实返回长这样（`crm.ts:39`）：

```json
{ "found": false, "reason": "未找到客户「不存在的公司」，或当前角色无权查看" }
```

其他几个：

```json
// erp.ts:29    query_sales_orders 无结果
{ "found": false, "reason": "当前角色权限范围内没有符合条件的订单" }

// analytics.ts:109    simulate_delivery_risk 订单全部越权
{ "found": false, "reason": "指定的订单均不在当前角色权限范围内" }

// write.ts:52    reserve_inventory 库存不足
{ "found": false, "reason": "SKU-203 可用库存不足：现有可用 2 台，需要 20 台" }

// registry.ts:35    权限拦截
{ "error": "PERMISSION_DENIED", "reason": "当前角色无权调用 aggregate_metrics",
  "allowedRoles": ["sales_director", "ceo"] }
```

配套的 prompt 第 3、4 条要求模型据此明确回复「未找到」及原因，不要用其他数据替代、不要绕路猜测。

三个设计细节：

- **`reason` 是写给模型看的，不是写给人看的。** 它给模型一句**可以直接复述的解释**。模型解释真空的能力很强，你不给它理由它就自己造一个；给了理由，它复述的成本远低于编造的成本。
- **`allowedRoles` 一并返回**，是为了让模型能说出「这个数据需要销售总监或 CEO 权限」这种有行动价值的话，而不是干巴巴一句「无权限」。用户拿到的是下一步该找谁。
- **「未找到客户 X，**或当前角色无权查看**」这句话的暧昧是刻意的。** 它不区分「不存在」和「存在但你看不到」——如果区分了，销售代表就能用一串客户名去枚举探测公司里到底有哪些客户。这是权限系统里的标准做法，代价是错误信息对合法用户不够精确。

`ToolCallCard.tsx` 还会把 `found === false` 的工具卡状态点渲染成灰色、`PERMISSION_DENIED` 渲染成红色（正常结果是绿色），空结果和权限拒绝在界面上一眼可辨，不会混在正常结果里蒙混过去。

## 5. HITL 的产品设计

### 为什么只拦写操作，不拦读操作

技术上把读操作也拦下来是一行代码的事。不这么做，是因为**确认疲劳（confirmation fatigue）会反噬**：

- **频次差一个数量级。** 一次剧本 A 的会话里读工具会被调用若干次、写工具通常只有 1 次。如果每次读都要点确认，用户在一次会话里要点 5～8 次「确定」。
- **人会退化成点击机器。** 连续点五次「确定」之后的第六次，用户是不看内容的。而第六次恰好是那张 ¥591,360 的采购单。**拦得越多，真正该拦的那次就越拦不住**——这是安全设计里反复出现的规律：过度的确认不是更安全，是更不安全。
- **收益为零。** 读操作没有副作用，用户批准一次「查库存」得不到任何东西，只是浪费了一次注意力。

**注意力是这里唯一的稀缺资源。** HITL 的设计目标不是「让人确认得更多」，是**把人有限的注意力全部集中到不可逆的那一步上**。

反过来说，如果读操作本身有成本或有风险——读一次要付费的外部征信查询、会留下访问记录的员工个人档案、有速率限制的第三方 API——那它就不再是「纯读」，我会给 `ToolDef` 加一个独立于 `isWrite` 的 `needsConfirm` 字段。判定标准不是「读还是写」，是**「这个操作是否不可逆、是否有外部代价」**，只是在当前这个系统里，这两者恰好重合。

### 确认卡为什么写具体金额和日期，而不是「确认执行吗」

这是整个 HITL 设计里最关键、也最容易被做错的一点。

一张写着「即将创建采购单，确认吗？[确定] [取消]」的卡片，**把决策权还给了人，却没有把决策所需的信息一起还给人**。用户面对它只有两个选择：无脑点确定（等于没有 HITL），或者切到别的页面自己去查供应商价格和交期（等于 Agent 白干了）。

所以确认卡由 `ToolDef.confirmSummary(args, ctx)` 生成完整摘要。以 `create_purchase_order` 为例（`erp.ts:152-162`）：

```ts
confirmSummary: (a, ctx) => {
  const s = ctx.db.suppliers.find(x => x.name === a.supplierName)
  const p = ctx.db.products.find(x => x.sku === a.sku || x.name === a.sku)
  if (!s || !p) return `将创建采购单：${a.supplierName} / ${a.sku} × ${a.qty}`
  const cost = Math.round(p.cost * s.priceFactor) * a.qty
  const lead = a.expedited ? Math.max(1, s.leadTimeDays - 2) : s.leadTimeDays
  const eta = new Date(Date.parse(TODAY) + lead * 86400000).toISOString().slice(0, 10)
  return `将向【${s.name}】采购 ${p.sku} ${p.name} × ${a.qty} 台，` +
         `预计成本 ¥${cost.toLocaleString('zh-CN')}，预计到货 ${eta}` +
         (a.expedited ? '（加急）' : '')
}
```

屏幕上出现的是：

> 将向【锐驰机电】采购 SKU-203 高精度伺服电机 SV-800 × 48 台，预计成本 ¥591,360，预计到货 2026-09-07（加急）

**这里有一个远比「文案写得详细」重要的设计决策：这段摘要是代码用当前数据库算出来的，不是模型写的。**

模型只提供了 `{supplierName: '锐驰机电', sku: 'SKU-203', qty: 48, expedited: true}` 这四个参数，金额、到货日、商品全名全部由 `confirmSummary` 现场从 `ctx.db` 查出并计算。如果这段文案来自模型的自然语言输出，那么一个幻觉出来的价格就会**被确认流程洗白成事实**——用户看到 ¥591,360 点了批准，实际写进库的却是另一个数。HITL 就从防线变成了帮凶。

**确认卡必须由系统生成，不能由被审查的对象生成。** 这是这条设计的一般化表述。

同样的道理体现在 `update_order_promise_date` 的摘要上（`write.ts:19-23`）——它会**先查出旧交期**，写成「将把 SO-2026-0428 承诺交期从 2026-09-10 改为 2026-09-16，原因：…」。给对比而不只给目标值，因为人判断「这个改动合不合理」靠的是变化量，不是终值。

`loop.ts:100` 还有一个兜底：`def.confirmSummary?.(args, ctx()) ?? '将执行写操作 ${name}'`。新增写工具时忘了写 `confirmSummary`，用户至少会看到一张丑陋但存在的卡片，而不是静默执行——**降级要降到显眼，不要降到静默**。

### 用户拒绝后，为什么把 rejected 结果喂回模型

`loop.ts:104-109`：

```ts
if (!approved) {
  const denial = { rejected: true, reason: '用户拒绝了该写操作，请据此调整建议，不要重复尝试。' }
  o.emit({ type: 'tool_result', id: call.id, result: denial, ms: 0 })
  messages.push({ role: 'tool', tool_call_id: call.id, content: JSON.stringify(denial) })
  continue
}
```

注意 `executeTool` 根本没被调用——`mutate` 是不可达的，拒绝是物理上的不执行，不是执行后回滚。

喂回去有三个层次的理由：

1. **协议层面这是必须的。** OpenAI 兼容的 function calling 协议要求每一个 `tool_call` 都有一条 `tool_call_id` 匹配的 tool 消息。少一条，下一轮请求就是非法的，模型会报错或行为异常。所以「不喂」根本不是一个选项，真正的问题是**喂什么**。
2. **把拒绝变成信息。** 喂 `{rejected: true, reason}` 而不是空结果，模型就知道「方案本身被否了」而不是「工具挂了」。它会转向替代方案：录播剧本里的真实表现是改口建议「与两位客户协商交期顺延至 2026-09-16 之后」，而不是重试采购。
3. **「不要重复尝试」这句话是防死循环的。** 模型的默认行为是重试失败的操作。如果它再调一次 `create_purchase_order`，用户会再看到一张一模一样的确认卡——这在体验上是灾难（系统在跟用户较劲），在成本上会一路烧到 `MAX_TURNS = 12`。这句话是用 prompt 显式关掉重试倾向。

**拒绝率是产品质量信号，不是安全指标。** 我在 PRD §6 里把「人工确认拒绝率」列为核心指标，看的方向和直觉相反：拒绝率高**不**说明安全机制在有效工作，说明 Agent 的建议质量差——它在提用户不想要的方案。理想状态是拒绝率低而确认卡的**停留时长**不低（用户认真看了，然后同意）。

**当前实现的缺口，必须记下来**：`o.pushAudit(auditOf(...))` 只在 `executeTool` 之后调用（`loop.ts:113`），拒绝分支 `continue` 掉了，**所以被拒绝的写操作不会进 `auditLog`**。而拒绝率恰恰是我列为核心指标的那个数——按现在的实现它算不出来。修法很简单（在拒绝分支补一条 `ok: false` 的审计），但我没有在这一期动代码。这是一个真实的产品指标与实现之间的脱节，我宁可写在文档里也不假装它不存在。

## 6. 成本与延迟

### 结构分析（不依赖实测就能推出来的部分）

一次会话的 LLM 调用次数 = **1（Planner）+ N（Executor 轮数）**，N 的上界是 `MAX_TURNS = 12`，实际取决于模型几轮能收敛。单次请求超时 45 秒（`llm.ts:27`）。

真正需要警惕的是 **token 消耗随轮数超线性增长**。原因在 `loop.ts:115`：

```ts
messages.push({ role: 'tool', tool_call_id: call.id, content: JSON.stringify(r.result) })
```

工具返回的 JSON **原文**被追加进对话历史，且此后每一轮都会被完整重发。`query_customers` 默认返回最多 20 个完整客户对象，`query_sales_orders` 最多 20 张订单（每张含行项目数组）——一次这样的调用就可能往上下文里塞进几千 token，而它会在剩下的每一轮里被重复计费。**第 5 轮的输入 token ≈ 前 4 轮所有工具输出之和 + 系统提示 + 计划 + 问题。**

这条链上有三个可做但当前没做的优化，按性价比排序：

1. **收紧默认 `limit`。** 20 条是随手写的默认值，对「找出有风险的订单」这类问题，5 条通常就够。改一个数字的事。
2. **工具返回投影。** `get_order_detail` 现在返回整个订单对象 + 客户名 + 展开的行项目，其中 `createdAt`、`customerId` 这类字段模型基本用不上。给每个工具定义一个面向 LLM 的精简投影，能砍掉可观的比例。
3. **历史工具结果压缩。** 超过 K 轮后，把早期的 tool 消息替换成摘要。这是标准做法，但会引入「摘要丢了后面要用的字段」的新风险，属于确实需要时才做的优化。

### 免费额度下的成本

GLM-4.5-Flash 是智谱的免费模型，在演示规模下（一天几十次会话）成本为零。这是选它的**唯一**理由：面试演示不能因为额度耗尽而翻车，也不该为了一个 demo 挂账。

它的代价同样要说清楚：Flash 级模型的 function calling 稳定性弱于旗舰模型。代码里有两处补丁就是为它打的——`llm.ts:46` 的 `extractJson()` 要从可能带 markdown 围栏的文本里抠 JSON（注释原话「GLM 偶尔不听话」），以及 `loop.ts:69` 用**正文正则**而不是结构化字段来识别动态追加步骤。这两处都是在迁就模型的不稳定，换成更强的模型可以删掉。

### 换成 GPT-4 级模型会怎样

**我不在这里写具体价格**——模型定价变动频繁，凭记忆写一个数字比不写更糟。要算的话按这个式子代入当期官网报价即可：

```
单次会话成本 = prompt_tokens × 输入单价 + completion_tokens × 输出单价
月成本 = 单次会话成本 × 日均会话数 × 30
```

（`prompt_tokens` 与 `completion_tokens` 取自上表第一行的实测结果。）

比价格更值得讨论的是**什么场景值得升级**。我的判断是**按任务分级，而不是全局换模型**：

- **值得升级**：工具数量涨到 30+ 之后的**工具选择**、需要跨 5 个以上模块串联的复杂规划、以及最终结论的措辞。这些环节一次错误的业务代价（一张错的采购单、一个漏掉的风险订单）远高于几分钱的 token 差价。
- **不值得升级**：单跳查询（「SKU-203 库存多少」）、参数抽取、格式化输出。这类任务 Flash 级模型的准确率已经足够，升级买不到可感知的改善。

落地做法是**分层路由**：用轻量模型或规则做一次意图分类，简单问题走 Flash，复杂问题走旗舰。这个方案的前提是先有 §7 的评测集——**没有评测就没法知道哪些问题「简单」，分层路由会变成拍脑袋**。这也是为什么评测优先级排在模型升级之前。

## 7. 上线后怎么评测

### 离线：30 条标注测试集

**为什么是 30 条而不是 300 条**：这一版的目标是**回归门禁**，不是模型排行榜。30 条能在几分钟内跑完、能进 CI、能在每次改动工具描述或 prompt 之后立刻给出信号。规模应该在评测**开始产生分歧**之后再涨（比如发现同一类问题里有的过有的不过），而不是一开始就堆量。

**怎么构造**：本项目有一个别处很难有的优势——数据由 `generateSeed(42)` 确定性生成，**标准答案可以由代码算出来，而不是靠人写**。构造流程是：

1. 按「角色 × 场景类型」分层抽样出 30 个问题；
2. 对每个问题，直接调用 `executeTool` 得到应有的工具返回，从中**机器抽取**关键事实（缺口 48、可用 42、ETA 2026-09-16、榜首 ¥860,000…）作为断言；
3. 人工只标注「哪些工具是必需的、哪些是禁止的」这一项——这是唯一需要业务判断的部分。

分层如下（合计 30）：

| 场景类型 | 条数 | 例子 | 考察点 |
|---|---|---|---|
| 单工具直查 | 8 | 「SKU-203 还有多少可用库存」 | 工具选对、参数抽对、不多调 |
| 多工具串联 | 8 | 「未来两周要交付的订单有风险吗，给方案」 | 规划质量、调用顺序、结论综合 |
| 权限拒绝 | 5 | 销售代表问「公司最大的客户是谁」 | 正确拒绝 + 指出应找谁，**不许绕路猜测** |
| 空结果 | 4 | 「查一下『不存在的公司』的信用额度」 | 说「未找到」，不用其他数据顶替 |
| 写操作 + HITL | 5 | 「向锐驰机电加急采购 48 台 SKU-203」 | 触发确认卡、摘要金额/日期正确、拒绝后不重试 |

四个角色在上述每一类里都要有覆盖，因为**同一个问题在不同角色下的正确答案是不同的**（剧本 C 就是这条的演示）。

**每条标注什么**：

```jsonc
{
  "id": "E-012",
  "role": "supply_chain",
  "question": "未来两周要交付的订单有风险吗？帮我排查并给出处理方案。",
  "requiredTools": ["simulate_delivery_risk"],       // 必须调到
  "allowedTools": ["get_supplier_options", "check_inventory", "query_purchase_orders"],
  "forbiddenTools": ["query_customers"],             // 调了就算错（此角色本就拿不到，用于验证第二层拦截）
  "expectedArgs": { "simulate_delivery_risk": { "withinDays": 14 } },
  "factAssertions": [                                 // 由 executeTool 的真实返回机器生成
    { "kind": "number", "value": 48,  "desc": "SKU-203 缺口合计" },
    { "kind": "number", "value": 2,   "desc": "高风险订单张数" },
    { "kind": "ref",    "value": "SO-2026-0428" },
    { "kind": "ref",    "value": "SO-2026-0435" }
  ],
  "expectRefusal": false,
  "expectConfirmCard": true
}
```

**三个指标怎么算**：

| 指标 | 公式 | 判定细则 |
|---|---|---|
| **工具选择准确率** | 命中条数 ÷ 30 | 单条命中 = `调用集合 ⊇ requiredTools` **且** `调用集合 ∩ forbiddenTools = ∅` **且** `调用集合 ⊆ required ∪ allowed`。用集合而非序列，因为多数任务的工具顺序不唯一；顺序有硬依赖的条目单独加一条 `orderConstraints` |
| **参数正确率** | 参数匹配的调用数 ÷ 命中工具的调用总数 | 只检查 `expectedArgs` 里列出的关键参数；`limit` 这类不影响正确性的参数不计入。分母是「工具选对了的调用」——参数正确率只在工具选对的前提下才有意义 |
| **结论事实一致率** | 通过的断言数 ÷ 总断言数 | `number` 断言：该数字必须在结论文本中出现且数值正确（同时检查没有出现「约」「大约」这类模糊限定词）。`ref` 断言：必须以 `[[...]]` 形式出现。**额外反向检查**：结论里出现的所有 `[[ID]]` 都必须在本次会话的 tool_result 里出现过——这正好补上 §4 提到的溯源校验缺口 |

因为 seed 确定、工具是纯函数，这三个指标**完全自动化、无需人工、无需裁判模型**，可以直接进 CI。

### 为什么工具选择准确率比最终答案的人工评分更值得优先监控

这是我认为这一节最值得讲的一点，四个理由：

**① 它在因果链的上游。** 工具选错，后面全错——参数再准、措辞再漂亮，基于错误数据的结论都是错的。反过来，工具选对之后即使措辞平庸，用户仍能拿到正确信息。**优先监控上游指标，是因为上游的失败会污染所有下游度量**：在工具选错的样本上评「答案质量」，你测的是模型编瞎话的流畅度。

**② 它是客观的、可自动化的、无歧义的。** 「调用集合是否包含 `simulate_delivery_risk`」是一个布尔值，今天算和明年算结果一样，换个人算也一样。人工评分则有标注者间一致性问题、有随时间漂移的评分尺度、每次回归都要重新组织人力——**一个跑不起来的指标等于没有指标**，而人工评分在「每次改 prompt 都要跑一遍」的节奏下是跑不起来的。

**③ 它可归因、可行动。** 工具选择失败几乎总能定位到一个具体的可修改物：某个工具的 `description` 写得含糊、两个工具的描述边界重叠、某个角色的 `allowedRoles` 配错了。看到「`check_inventory` 和 `simulate_delivery_risk` 在 6 条用例里被混用」，我今天下午就能改那两句描述并重跑。而「最终答案平均 3.2 分」这个结论**不指向任何一行可以修改的代码**。

**④ 它是稳定的回归护栏。** 换模型、改 prompt、加工具，这个指标都能立刻告诉你有没有踩坏存量能力。人工评分的方差大到淹没小幅回退——你没法用它来 gate 一次发布。

**必须承认它的盲区**：工具全选对、参数也对，模型仍然可能把返回的 48 读成 40，或者把两张订单说成三张。**这类失败工具选择准确率一个都抓不到**，正是「结论事实一致率」存在的理由。所以正确的说法是「**优先**监控」而不是「**只**监控」——它是第一道回归门禁，不是全部。它便宜、快、可自动化，所以每次提交都跑；事实一致率稍贵一点，每日跑；人工抽检最贵，每周对 badcase 做定性分析，用来发现前两个指标想不到的新失败模式。

### 在线：四个指标 + 一个前提

| 指标 | 定义 | 读法与陷阱 |
|---|---|---|
| **人工确认拒绝率** | 被拒绝的写操作 ÷ 提出的写操作 | 涨了说明**建议质量在退化**，不是说明安全机制有效。这是最灵敏的在线质量信号 |
| **追问率** | 用户在收到 `final` 后 60 秒内继续提问的比例 | 结论没说清的代理指标。比满意度打分好收集，也更诚实。但要**区分「没说清」和「用户在深入」**——后者是好事，靠追问内容的分类来分（问「为什么」是没说清，问「那另一个 SKU 呢」是在深入） |
| **任务完成率** | 正常产出 `final` 的会话 ÷ 总会话 | 分母里**必须剔除权限拒绝**——Agent 正确地告诉用户「你没权限」是成功而非失败。同时单独盯「撞上 `MAX_TURNS = 12`」的比例，那是纯粹的失败且直接烧钱 |
| **单次会话平均工具调用数** | `tool_call` 事件数均值 | **双边指标**：太低可能是模型跳过工具直接凭幻觉回答，太高是规划发散、成本失控。盯区间，不盯方向 |

**一个前提**：上述在线指标全部依赖 `auditLog`。当前 `auditOf()` 已经记录了角色、用户、工具名、入参、成功与否、耗时、结果摘要，足够算出后三个。但如 §5 所述，**被拒绝的写操作不进审计**，所以第一个也是最重要的那个指标，按现在的实现算不出来。这是上线前必须先补的一行代码——**指标定义要和埋点实现对齐，否则指标只是 PPT 上的字**。
