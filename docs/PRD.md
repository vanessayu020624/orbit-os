# OrbitOS 产品需求文档

> 版本 v1.0（演示版）· 2026-09-02
> 系统内当前日期恒为 `TODAY = '2026-09-02'`，本文所有日期以此为基准。

---

## 1. 问题定义

B2B 分销商最贵的一堵墙立在销售和供应链之间。销售在签单现场承诺交期，他看得到客户、看得到价格，唯独看不到那颗 SKU 的可用库存和在途采购单的到货日；供应链看得到库存和 ETA，但等他发现某个型号被超卖时，合同上的交期已经白纸黑字。等问题浮上来，能做的只剩两件都不体面的事：花溢价加急采购，或者打电话跟客户道歉。

这不是数据不存在的问题——CRM 里有订单，ERP 里有库存和采购，两边都是真的。问题是**没有人负责把它们对上**。对账这件事跨部门、无人拥有、且只有在出事那一刻才显得重要，所以它永远排在每个人待办清单的最后一行。

OrbitOS 的赌注是：这类「跨系统、多步骤、有明确判断规则、但没人愿意天天做」的活，恰好是 Agent 的最佳落点。它不需要创造性，需要的是不知疲倦地把六个模块串起来查一遍，并且在发现问题时**带着处理方案**来找人，而不是丢一条告警。

## 2. 目标用户与场景

系统内置四个演示角色，对应四种截然不同的打开动机。

**销售代表（张伟，`sales_rep`）** —— 管着 9 个客户，年采购额从 86 万到 18 万。他在客户催货或准备报价时打开系统，要回答的问题是「我这单能不能按期交？要不要现在就跟客户改口？」。他关心的永远只有自己名下那一小块，看到全公司数据对他没有价值，反而是信息泄露。他有一个写权限：改自己订单的承诺交期（并留下原因）。

**销售总监（李娜，`sales_director`）** —— 管一个团队。她在周会前和月底冲刺时打开系统，要回答的是「团队漏斗健康吗、加权预测多少、哪几笔应收该催了」。她需要跨人看，但只跨到团队边界；她要的是聚合数字而不是明细。她能创建跟进任务，把结论直接派给下属。

**供应链主管（王强，`supply_chain`）** —— 演示的主角。他每天早上打开系统，问的是「未来两周要发的货，有哪些备不出来」。他要看全公司的订单（否则漏判），但**不需要知道每张订单卖了多少钱**——所以他看到的金额是 `***`。他也不需要客户联系人和商机，那与备货无关。他掌握两个最重的写权限：下采购单、锁库存。

**CEO（陈立，`ceo`）** —— 不常打开，一旦打开就是要一个全局判断：营收、TOP 客户、漏斗结构、逾期应收。他能看全公司任何数据，但**一个写操作都没有**。理由见 §5。

## 3. 功能范围

**做什么**

- 六个业务模块的只读界面：客户、商机、订单、库存、采购、应收，全部按角色过滤（空态文案本身就是权限的可见证明）。
- 实时 BI 仪表盘：Agent 主动风险卡、四张 KPI、三张图表，每 4 秒推进一条模拟业务事件。
- 常驻 AI Sidekick：自然语言提问 → 显式计划 → 逐步工具调用（过程全部可展开）→ 带溯源标记的结论。
- 15 个工具组成的 Agent 能力面，按角色切成四套；写操作强制人工确认。
- 一键角色切换与一键重置演示数据。
- `/api/chat` 不可用时的录播降级模式（带明示角标）。

**明确不做**（继承自设计文档 §2 的非目标，并在实现中被严格守住）

- 真实数据库、用户注册、JWT 鉴权 —— 用一键角色切换替代。演示要证明的是「权限如何约束 Agent」，不是「登录怎么写」。
- 多租户、审批工作流引擎、财务 / HR / 生产模块。
- Agent 长期记忆、多 Agent 协同、RAG 知识库 —— 这些是 V2 的事（§7），塞进 V1 只会让每一项都做不深。
- 移动端适配 —— 面向投屏演示，桌面宽屏优先。
- 字段级动态脱敏配置 —— 供应链角色的金额脱敏直接写死在 `maskOrderForRole()` 里。做成可配置需要一套规则 DSL 和管理界面，而演示里它只需要在屏幕上出现一次 `***`。

减法的理由是统一的：这个产品要在 8 分钟里讲清三件事（自主规划 / 权限是真约束 / 人机协同闭环），任何不服务于这三件事的功能都会稀释叙事。

## 4. 核心流程（剧本 A：交期风险穿透排查）

以供应链主管王强的视角，一次完整的用户旅程：

1. **发现** —— 王强打开仪表盘。他没有提问，系统已经在页面顶部摆好一张红色风险卡：「**2 张订单存在交期风险**／SKU-203 高精度伺服电机 SV-800 缺口 48 台，最早到货 2026-09-16」。同一口径的数字也出现在 KPI「交期风险订单 = 2」上。这一步的产品意图是：**Agent 主动来找人，而不是等人来问**。

2. **提问** —— 他点卡片右侧的「让 Agent 排查 →」。这个按钮通过事件总线把一句预置问题灌进 Sidekick 并直接开跑，不需要打字。

3. **规划** —— Sidekick 先渲染出一份带勾选框的计划清单（目标 + 3～6 个步骤）。他在真正的执行开始前就知道 Agent 要查哪几件事，也就有了「不对就打断」的机会。

4. **执行** —— 计划逐条打勾，每步对应一张可展开的工具调用卡，露出入参、出参 JSON 和耗时。关键一步是 `simulate_delivery_risk`：它按交期升序累积扣减库存，算出 SO-2026-0428 缺 28 台、SO-2026-0435 缺 20 台，合计 48 台；并顺带查到唯一在途采购单 PO-2026-0117 的 ETA 是 2026-09-16，晚于两张订单的交期 5～6 天。

5. **决策支持** —— Agent 调 `get_supplier_options` 比选供应商：锐驰机电交期 7 天、准时率 94%、价格系数 1.12；东瑞传动交期 14 天、准时率 78%、价格系数 1.00。它给出的不是「有风险」，而是「向哪家、买多少、贵多少、几号到」。

6. **人工确认（HITL）** —— Agent 要调 `create_purchase_order`，执行被拦下，弹出确认卡：「将向【锐驰机电】采购 SKU-203 高精度伺服电机 SV-800 × 48 台，预计成本 ¥591,360，预计到货 2026-09-07（加急）」。**决策权在人手里，而人手里有做决策所需的全部数字。**

7. **落库与反馈** —— 王强点「批准执行」，采购单写入 store，可用库存补足。他切回仪表盘：红色风险卡消失了，KPI「交期风险订单」从 2 变成 0。

8. **溯源** —— 结论文本里的 `[[SO-2026-0428]]`、`[[SKU-203]]`、`[[PO-2026-955]]` 都是可点击的 chip，点一下跳到对应列表页核对原始记录。

如果王强点的是「拒绝」，流程不会中断：拒绝结果被喂回模型，Agent 改口给出替代方案（与客户协商交期顺延至 ETA 之后），并且不会再试一次采购。

## 5. 权限模型

| 能力 | 销售代表<br>张伟 | 销售总监<br>李娜 | 供应链主管<br>王强 | CEO<br>陈立 |
|---|:--:|:--:|:--:|:--:|
| 可用工具数 | **9** | **11** | **8** | **11** |
| 客户 / 商机 | 仅本人名下 | 本团队 | ✗ 无权 | 全公司 |
| 销售订单 | 仅本人名下 | 本团队 | 全公司（**金额 `***`**） | 全公司 |
| 库存查询 | ✓ | ✓ | ✓ | ✓ |
| 采购单 / 供应商 | ✗ | ✗ | ✓ | ✓ |
| 应收账款 | ✗ | ✓ | ✗ | ✓ |
| 聚合指标 `aggregate_metrics` | ✗ | ✓ | ✗ | ✓ |
| 交期风险测算 | ✓（本人订单） | ✓（本团队） | ✓（全公司） | ✓（全公司） |
| 改承诺交期 | ✓ | ✓ | ✗ | ✗ |
| 建跟进任务 | ✓ | ✓ | ✗ | ✗ |
| 建采购单 / 锁库存 | ✗ | ✗ | ✓ | ✗ |
| **写权限合计** | 2 | 2 | 2 | **0** |

两点值得展开：

**为什么 CEO 没有写权限。** 因为权限映射的是**职责边界**，不是行政层级。CEO 不是采购员也不是销售，他不会亲手下一张采购单——真让他能下，反而绕过了供应链的库存校验和采购流程责任人。把「谁能看」和「谁能改」拆开是企业系统的基本功：看的权限跟着信息需求走，改的权限跟着岗位职责和问责走。这条设计还有一个演示上的好处——它能直接反驳「你的权限模型就是按官大小排的」这种质疑。

**为什么供应链能看全部订单却看不到金额。** 他必须看全公司订单才能算准备货（漏掉任何一张都会误判），但订单金额与备货决策无关，属于该给多少给多少的最小权限原则。实现上是 `maskOrderForRole()` 把 `totalAmount` 和每行 `unitPrice` 替换成 `***`，SKU 和数量保留——这比整条记录不给更实用，也更接近真实企业里的字段级权限。

权限的实现细节（为什么放在工具层而不是 UI 层）见 [`agent-design.md`](agent-design.md) §3。

## 6. 成功指标

演示能力必须能翻译成业务方愿意为之付钱的指标。分两组：

**业务结果指标（证明这东西有用）**

| 指标 | 定义 | 为什么是它 |
|---|---|---|
| 交期风险发现提前期（天） | 风险被识别的日期与承诺交期的间隔中位数 | 这是本产品的核心价值。从「发货前一天发现」到「提前 8 天发现」，决定了还有没有加急采购这个选项 |
| 缺货导致的延期订单率 | 因库存缺口延期交付的订单数 ÷ 期间总交付订单数 | 前一个指标的最终兑现。提前期涨了但延期率没降，说明发现了没人处理 |
| 加急采购溢价占比 | 加急采购的溢价金额 ÷ 采购总额 | 反向护栏。如果延期率靠无脑加急压下来，成本会在这里冒出来 |

**产品健康指标（证明 Agent 本身在工作）**

| 指标 | 定义 | 为什么是它 |
|---|---|---|
| Agent 建议采纳率 | 被批准执行的写操作数 ÷ 提出的写操作数 | 直接衡量建议质量 |
| 人工确认拒绝率 | 1 − 采纳率 | **拒绝率高不是安全机制在起作用，是建议质量差。** 这是本产品最重要的质量信号，见 `agent-design.md` §5 |
| 单次问询平均工具调用数 | 一次会话内 `tool_call` 事件数的均值 | 太低说明 Agent 在偷懒直答（幻觉风险），太高说明规划发散、成本失控。这是个双边指标，要盯区间不是盯方向 |
| 任务完成率 | 正常产出 `final` 事件的会话数 ÷ 总会话数 | 分母里要剔除权限拒绝这类**正确的**不完成 |
| 追问率 | 用户在收到结论后 60 秒内继续提问的比例 | 结论没说清的代理指标，比满意度打分好收集得多 |

离线评测集怎么构造、工具选择准确率怎么算，见 `agent-design.md` §7。

## 7. 迭代规划

**V2 · 接真实 ERP。** 当前 15 个工具全部读写 `DbSnapshot` 这份内存快照，但它们对外只暴露 `ToolDef` 契约（`parameters` / `allowedRoles` / `isWrite` / `run`）。接真实系统要做的是把 `run` 的实现换成 SAP / 用友 / 金蝶的 API 调用，契约、权限声明、HITL 逻辑、前端全部不动——**工具层是唯一的耦合点**。真正的工作量不在这里，在于真实 ERP 的字段语义对齐（「可用库存」在不同系统里的口径差异）和调用延迟（本地计算 4ms，真实 API 可能 800ms，会逼着重新设计并行调用和超时降级）。

**V2 · Agent 记忆。** 现在每次提问都是冷启动。最有价值的记忆不是聊天历史，而是**决策偏好**：「王强连续三次拒绝了向东瑞传动的采购」应该沉淀成下次比选时的排序权重。做法上倾向于结构化偏好表而非向量库——可解释、可编辑、可审计，用户能看见系统记住了什么并且能删掉它。

**V2 · 多 Agent 分工。** 当工具数从 15 涨到 50+，单个 Executor 的工具列表会开始互相干扰（描述相似的工具被误选）。届时按域拆成销售 Agent / 供应链 Agent / 财务 Agent，由一个 Router 分派，跨域任务走 Agent 间移交。**触发条件是工具选择准确率跌破阈值，而不是「多 Agent 听起来更高级」**——多 Agent 会显著增加延迟和调试难度，没到那个规模不该上。

**V2 · 审批流引擎。** 当前 HITL 是单点确认：谁在用就谁批。真实企业里 ¥591,360 的采购单需要走金额分档审批，且发起人不能是审批人。这要把「确认」从一个同步的 Promise 变成一个有状态、可异步、可追溯的审批实例——是产品复杂度的一次真正跃升，也是 `AuditLog` 从演示道具变成合规基础设施的时刻。
