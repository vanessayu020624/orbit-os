0.3　事实分级制度：为什么每个数字都要标来源

AI 产品文档最容易腐烂的地方是数字。「响应约 1.2 秒」「准确率大概 90%」「一次问询大约 3000 token」——这些句子写起来毫无阻力，读起来也顺，但没有一个能被验证。一旦其中任何一个被追问「你怎么测的」而答不上来，整份文档的可信度会一起塌掉，包括那些本来是真的部分。

所以本册对每一个事实性数字强制标注来源等级：

标记含义取用规则
代码事实直接读自本仓库源码或由纯函数确定性算出，附 文件:行号可直接引用。种子固定（generateSeed(42)）意味着这类数字任何人任何时候重跑都一致
已实测在真实环境跑出来并被记录的观测值，附测量条件可引用，但必须连同样本量与测量条件一起引用——本项目多数实测样本量极小（n=1~9），见 §5.4
估算由已实测值经明确推算式导出必须写出推算依据。不得与实测值并列呈现而不加区分
待实测尚无观测数据一律不填具体值，只填测量方法与责任归属。这是本册最硬的一条规矩
这条规矩带来的代价，我认了

坚持这条规矩的直接后果是：本册第 5、6 章里有相当数量的格子写着「待实测」而不是一个好看的数字。一份到处是「待实测」的评估报告，第一眼观感一定不如一份填满数字的。

但两者的区别是：填满数字的那份，只要有一个数被追问出处，剩下的数字全部失去意义；而这一份，标了代码事实的每个数字都能当场翻到代码行验证。我宁可交一份有空格但每个填了的格子都站得住的表，也不交一份满格但没人敢引用的表。

更实际的理由：这些空格不是遗漏，是排期。§6.8 的上线门槛表里，每一个「待实测」都对应一条上线前必须补齐的验证任务，附测量方法与判定阈值。空格本身就是待办清单。

1.1　行业与经营现实：B2B 工业品分销商在赚什么钱

这门生意的利润结构决定了它的风险结构。以埋雷场景中的核心 SKU 为例代码事实：P-003 高精度伺服电机 SV-800，单价 18,600 元，成本 11,000 元，毛利率 40.9%。一台缺货导致的延期交付，赔付与客户流失的代价远高于单台毛利 7,600 元。也就是说：

经营现实

分销商的核心竞争力不是价格（上游供货价对同行差异有限），而是交付确定性——「你说 9 月 10 号到，就得 9 月 10 号到」。而交付确定性的最大敌人，是「答应了才发现没货」。这个错误的发生点在销售侧，代价的承担点在供应链侧和客户关系侧，因此天然没人对它负责。

1.4　替代方案盘点：六种做法的横向对比

「为什么不用现成的」是这类项目最该先回答的问题。下面六种是这个痛点在现实中真实存在的解法，逐一评估。

方案怎么做为什么不够本方案的差异点
A. 人工跨系统核对
现状基线		 销售问供应链、供应链查 ERP、拉群拍板 成本高且不稳定：依赖具体人的经验与当天心情；只在有人想起来时才发生——而绝大多数漏单恰恰是没人想起来 把「想起来」的成本降到问一句话，触发门槛从「怀疑有问题」降到「顺手确认」
B. BI 看板 / 报表 Tableau、FineBI 做一张「交期风险」看板 这是最强的竞品，也是最容易被低估的。看板能算准同样的数。但看板是预定义问题：谁定义的问题它才答。「这三张单里哪张该先保、加急采购划不划算」不在任何一张看板上，因为这个问题只在特定情境下出现一次 处理长尾的、一次性的、跨表的追问；且能在同一轮对话里从「查」走到「改」
C. ERP 自带预警 库存低于安全库存时报警 阈值预警在本场景直接失效：P-003 可用 42 > 安全库存 30，不触发任何告警，但实际已缺口 48 台。因为风险来自「未来的承诺」而非「当下的存量」代码事实 按承诺交期时间轴推演台账，而不是比阈值
D. 定制开发一个「交期风险」模块 让 IT 写死这条规则做成一个页面 规则本身值得写死——本项目就写死了（risk.ts）。但下一个跨表问题又要再排期三个月。企业里这类问题是长尾，逐个定制的边际成本不下降 规则层复用同一套工具，交互层由模型组合，新问题不需要新页面
E. 通用 Chat（把数据粘给 ChatGPT） 导出 Excel 贴进对话框 三个致命问题：① 没有权限边界，销售能看到全公司数据；② 数字靠模型「读」出来，无法追溯；③ 只能读不能写，结论落不了地 三层 RBAC + [[ref]] 数字可溯源 + 写操作 HITL（见 §2.5、§2.6）
F. RPA / 定时脚本 每天跑一遍脚本，有风险就发钉钉 能覆盖已知风险模式，且成本低。但只能回答被编码过的那一个问题，无法追问「那怎么办」，也无法在同一入口执行处置 可以并存——F 负责主动推送，本方案负责推送之后的所有追问与处置
诚实的结论：不是所有场景都该用 Agent

上表里 B（BI 看板）和 F（定时脚本）在各自适用的场景中比 Agent 更优——更便宜、更稳定、不会胡说。一个 AI PM 如果说不出「哪些情况下不该用我的产品」，那说明他没有真正评估过。

本方案的适用边界是明确的三条：① 问题是长尾的（预定义看板覆盖不到）；② 需要跨 2 个以上数据域；③ 结论之后紧跟着一个动作。三条同时成立时 Agent 有优势；只满足一条时，看板或脚本是更好的选择。第 5.2 节把这个判据形式化为可打分的五维框架，并用它把 18 个原子任务逐个分流。

1.5　价值假设与规模测算（含敏感性分析）

这一节是本册最需要小心的地方。我没有这家（虚构）公司的真实运营数据，所以任何绝对金额都是假设而非事实。处理方法是：把价值拆成一个显式公式，把每个参数标成假设，然后做敏感性分析——重点不在于算出一个数，而在于说清这笔账在什么条件下成立、在什么条件下不成立。

1.5.1　价值公式

年化价值 = V_avoid + V_time − C_run

V_avoid（避免的违约损失）
  = 年交付风险单量 × 当前漏检率 × 系统检出提升 × 单次违约成本

V_time（节省的核对时间）
  = 年核对次数 × 单次节省分钟 × 人力单位成本

C_run（运行成本）
  = 年会话数 × 单次 token 成本  +  维护投入

1.5.3　敏感性分析：这笔账在什么条件下成立

与其编造一个总额，不如反过来求盈亏平衡点——这是在参数未知时唯一诚实且有用的做法。设：

  • 年风险订单数 N = 480 × 8% ≈ 38 张
  • 系统相对人工的净增检出率为 Δ（待实测）
  • 单次违约成本 L（待实测）
  • 年运行成本 C（待实测）

则成立条件为 38 × Δ × L > C。代入不同假设：

若净增检出率 Δ每年多拦下的订单则单次违约成本 L 需高于（设年运行成本 C = 5 万元）
10%（保守）约 3.8 张约 1.3 万元 / 张
20%（中性）约 7.6 张约 6,600 元 / 张
30%（乐观）约 11.4 张约 4,400 元 / 张
这张表真正说明的事

把它和代码事实对照：P-003 单台毛利 7,600 元，而一张典型订单是 20~40 台。即便只按「延期一张 30 台订单造成的直接损失等于该单毛利的 10%」这一极度保守的口径估，单次违约成本也在 2 万元量级——远高于上表任何一档的盈亏平衡线。

结论：只要系统的净增检出率不低于 10%，这笔账在极宽的参数范围内都成立。价值论证的压力因此全部转移到一个可测量的问题上——Δ 到底是多少。这正是 §6.6 实验组 C 存在的理由，也是本册把大量篇幅放在评测设计而非价值宣传上的原因。

2.2　断点归因：为什么这五处必然断

五个断点不是执行不力，是流程结构的必然产物。归因如下：

断点结构性原因为什么加强管理解决不了该由谁解决
①权限按组织职能划分，而问题按业务链路发生放开权限会引入数据泄露风险（销售能看到全公司库存与成本）；不放开就必须人工中转代码：三层 RBAC 在角色边界内提供只读投影（§2.6）
②ERP 的 available 字段语义是「当前未被占用」，不含「未来将被占用」这是数据模型语义问题，培训改不了字段含义代码：simulateDeliveryRisk 按承诺交期升序推演台账（纯函数、确定性）
③承诺动作发生在三个人的三个时刻，无串行化点要求「承诺前先报备」等于给每单加一道审批，销售会绕开代码：同上，推演天然覆盖全部待发货订单
④阈值告警是存量模型，风险是流量问题调低安全库存阈值只会制造大量误报代码：风险分级用 ETA 与承诺日期之差，不用阈值
⑤没有人被指派在「承诺之后、到期之前」这个窗口做检查指派了也没人做——这活的收益归公司，成本归个人（§1.2）模型：把检查的触发成本降到问一句话
归因得出的分工原则

看最后一列：五个断点里四个该由代码解决，只有一个该由模型解决。这不是保守，是准确——①~④ 都是「规则明确、只是没人执行」，把明确的规则交给概率模型是自找麻烦；⑤ 是「规则明确但不知道何时该执行」，这才是语言模型的位置。

模型的价值在于降低触发成本与表达成本，不在于计算。这条原则在第 5 章会被扩展成 18 个任务的逐个判定，并且在代码里已经落实：所有数值计算都在工具的 TypeScript 里完成，模型只负责选工具、填参数、把结果讲成人话。

为什么是 Planner–Executor 两段式，而不是纯 ReAct

纯 ReAct（想一步做一步）在企业场景有两个具体问题：① 用户在第一秒看不到 Agent 打算干什么，只能盯着转圈；② 无法在执行前判断本次是否涉及写操作，HITL 的准备工作没有着力点。

两段式的代价是多一次 LLM 调用（首字延迟增加），换来的是：计划先行渲染给用户（可预期）、needsWrite 在执行前已知（可预防）、以及计划本身成为一个可评测的中间产物——工具选择准确率能在不跑完整链路的情况下单独回归（§6.2）。第三点是评测体系能成立的前提，这是选择两段式最实际的理由。

补偿设计：Executor 允许在执行中发现计划不足时追加步骤（plan_amended 事件，正则 /需要追加步骤[：:]\s*(.+)/ 提取），保留了 ReAct 的适应性。

已知不足：这条原则目前只有 create_purchase_order 完整做到（查库算成本与 ETA）。create_followup_task 和 reserve_inventory 的摘要是纯参数回显、零查库。这是一处真实缺口，登记为 G-01（§3.7）。

2.7.1　模型不调用工具时的三道兜底

最常见的失败模式不是模型调错工具，而是模型不调工具、直接用常识编一段话。代码里有三道针对性防线代码事实：

这句话是本产品降级策略的浓缩：AI 是增量能力，不是系统的承重墙。模型挂了，OrbitOS 退化成一个普通的 CRM/ERP 前端，用户该查的还能查。一个把核心业务流程架在模型可用性上的设计，在企业环境里是不可接受的——这也是为什么全部 5 个数据页面都不经过 Agent 独立可用（§4.1）。

2.7.3　用户拒绝写操作后的流程

拒绝不是终止。userDeclined = true 后有三个连锁效果代码事实：① 跳过 executeTool 与审计留痕（拒绝的操作不该进审计流水）；② 向模型回灌明确指令「请据此调整建议，不要重复尝试」——防止模型换个参数再试一次这种令人恼火的行为；③ 关闭 Guard A（既然用户主动拒绝了，此后模型不调工具就直接收尾，不再催促）。

第三点值得单独说：拒绝之后模型不调工具是合理的，因为它已经无路可走，此时应该做的是解释和给替代方案，而不是被系统逼着再调一次工具。把「用户拒绝」这个信号正确传导到后续所有分支，是 HITL 从「一个弹窗」变成「一条完整流程」的分界线。

3.1　产品定位与设计原则

一句话定位：OrbitOS 是一个打通 CRM 与 ERP 数据的企业运营 Agent —— 它在每个员工自己的权限边界内，把跨系统的交叉核对压缩成一句话，并在结论之后允许直接执行处置动作，但每一次写入都必须由人确认。

五条设计原则

原则含义在代码中的体现
P1　模型只做判断，代码只做规则凡是能用确定性代码算准的（金额、缺口、日期差、风险等级），一律不交给模型risk.ts 全部数值计算为纯函数；confirmSummary 现查数据库；模型的输出里不应出现它自己算出来的数
P2　每个数字必须可核对回答中的实体标识必须是用户能在 UI 里翻到的那一个present.ts 投影层：只暴露业务单号（SO-2026-0412 / SKU-203），不暴露内部主键（SO-001 / P-003）；[[ref]] 角标可点击定位
P3　写操作必须由人拍板Agent 可以准备一个动作，但不能替人做决定4 个写工具全部 HITL 拦截；确认摘要由代码生成（§2.5）
P4　边界要说出来，不能装作没有看不到的数据要告知存在，而不是当作不存在scope.hidden 披露；Executor 规则 4a 明令禁止「全公司只有 N 个」这类表述
P5　AI 挂了系统还得能用Agent 是增量能力，不是承重墙5 个数据页面完全不经过 Agent；失败卡后紧跟「不依赖模型的数据现在就能查」

3.2　目标与非目标

本版本要做的本版本明确不做的
  • 四角色权限隔离的对话式查询（读）
  • 跨 CRM/ERP 的交叉推演（交期风险）
  • 写操作的 HITL 确认与审计留痕
  • 数字可溯源（[[ref]] 角标 + 无法解析时标红）
  • 不依赖模型的 5 个数据页面 + 仪表盘
  • 会话按角色隔离、可归档
  • 不做真实 ERP/CRM 对接——数据为固定种子生成，目的是可复现与可回归
  • 不做主动推送——风险需用户提问才触发（缺口 G-03）
  • 不做跨会话长期记忆——单会话内最近 6 轮原文 + 更早轮次折叠成 300 字摘要，会话之外不留存
  • 不做模型微调——全部能力来自 prompt + 工具设计
  • 不做移动端
  • 不做多租户——单公司单实例
这个参数被定错过一次，值得单独讲

最初的值是最近 2 轮，理由写得很像回事：企业数据问答的典型会话是 1~3 轮，长程记忆收益低；而历史要同时进 Planner 和 Executor 的 system prompt，token 成本近似线性增长，旧数据还会与新结果冲突诱发幻觉。

这套推理唯一的问题是：它假设的会话形状不是真实的会话形状。真实的追问链是「查风险 → 看某张订单 → 问这个客户的应收 → 回头说『用方案 1』」——到第四问时第一问已经掉出窗口，模型会把「方案 1」理解成刚才那个客户的事。2 轮够接住紧邻指代，接不住跨话题回指。

现值是 HISTORY_TURNS = 6 原文 + 更早轮次滚动折叠成 SUMMARY_MAX = 300 字摘要（summarize.ts）。不无限往上加的原因仍然是成本：Executor 的 system prompt 本身就带工具目录，历史每多一轮都要乘进后面每一次 function calling 的往返。

可迁移的一点：上下文窗口大小不是一个可以拍脑袋定的常数，它取决于「用户的指代最远指向多久之前」。这个距离只能靠观测得到，所以 §6.3 的「会话轮次分布」埋点不是锦上添花——它是这个参数唯一的校准依据。

3.5.2　工具边界的三条判据

判据说明正例 / 反例
① 一个工具 = 一个业务问题不做「万能查询工具」，因为参数空间越大模型填错的概率越高正例：simulate_delivery_risk 直接回答「哪些单会晚」；反例：如果只给 query_orders + check_inventory，模型必须自己做台账推演——而它一定会算错
② 计算留在代码，不留给模型凡涉及数值推演的，封装成工具而非让模型多次调用后自行汇总aggregate_metrics 返回聚合结果而非明细；模型拿到的就是最终数
③ 写操作粒度对齐审批单元写工具的粒度必须等于用户一次点「批准」愿意承担的责任范围正例：create_purchase_order 一次一单；反例：批量下单工具——用户无法对一个批次做出有意义的确认
最能说明判据 ① 的一个例子：simulate_delivery_risk 为什么必须存在

假设不提供这个工具，模型要回答「哪几单会晚」必须：查库存拿到 42 → 查订单拿到三张单及各自数量与承诺日 → 按日期排序 → 逐单扣减台账 → 比对在途 PO 的 ETA → 判定风险等级。加粗部分是纯计算，而语言模型做多步算术的可靠性众所周知。

更糟的是这类错误看起来完全正常——它会输出一个格式正确、语气笃定、数字错误的答案。而这恰恰是企业场景里最危险的失败模式。

所以：凡是「规则明确、多步推演、错了不易被发现」的计算，一律封装成工具。模型的职责缩减为「判断此刻该调这个工具」和「把结果讲成人话」——这两件事它做得比人好，而算术它做得比代码差。

3.5.3　工具描述即产品文案

工具的 description 字段是模型选择工具的唯一依据，因此它是写给模型看的产品文档，需要按产品文案的标准打磨。本项目的三条约定：

  • 写清楚「什么时候用」而不只是「这是什么」——例如 simulate_delivery_risk 的描述强调「当需要判断现有订单能否按承诺交期交付时使用」，而不是「模拟交付风险」。
  • 写清楚返回什么——让模型能预判是否需要再调其它工具，减少无效轮次。
  • 默认值写进描述——这一条目前没做好：多数工具的 limit 默认值 ?? 20 写在代码里、不在 schema 描述中，模型不知道自己不传 limit 会得到 20 条。登记为 G-04。

V2 的准出条件写的是「真实数据下 L1 指标不低于模拟数据下的 90%」，而不是「接入完成」。

原因：本项目全部指标都建立在固定种子生成的数据上——数据干净、字段完整、无脏值、无歧义命名。真实 ERP 里同一个客户可能有三个名字、订单状态字段可能有历史遗留的枚举值、库存表可能有负数。模拟数据上的高准确率不能外推到真实数据。

4.4　四类卡片的交互规格

4.4.1　计划卡（PlanCard）

提问后第一个出现的元素。逐条列出步骤，当前步骤高亮。若执行中触发 plan_amended，追加一条并标注为「已追加」。

已知问题：步骤高亮由 stepIdx 驱动，而 stepIdx 按 LLM 轮次递增而非按实际步骤推进，因此高亮位置可能与真实进度不符（缺口 G-08）。

4.4.2　工具调用卡（ToolCallCard）

状态点颜色触发条件优先级（同时满足时取上）
进行中橙色 · 脉冲已发起、未返回1
无权红色返回 PERMISSION_DENIED2
无结果灰色返回 found === false3
成功绿色其余4

卡片默认折叠，仅显示工具名与参数摘要；点击展开显示完整入参与返回值。

为什么工具调用要给用户看

常见做法是把工具调用藏起来，只给最终答案——理由是「用户不关心技术细节」。这在消费级产品里成立，在企业决策场景里不成立。

因为用户要为基于这个答案做出的决定负责。他需要能判断「这个结论是查了什么得出的」，尤其是当结论与他的直觉冲突时。把工具调用做成可折叠而非隐藏，是把「信任」变成「可验证」的成本最低的做法——不想看的人不受打扰，想核对的人一点就能看到。

红色（无权）和灰色（无结果）两个状态尤其重要：它们让用户看到Agent 试过但没成功，而不是让 Agent 悄悄绕过去然后给一个基于不完整数据的答案。

4.4.3　确认卡（ConfirmCard）

状态视觉内容与操作
待确认橙色边框动作摘要（代码生成）+ 影响说明 + [ 批准执行 ] / [ 拒绝 ]。CEO 跨职能时前置越权提示
已批准绿色「✓ 已批准并执行」，按钮消失
已拒绝灰色「已拒绝，Agent 将调整建议」，按钮消失

两个刻意的设计选择：①「拒绝」不是危险色（红色）——拒绝是正常且被鼓励的操作，不该被视觉暗示为异常；② 拒绝后的文案是「Agent 将调整建议」而不是「已取消」——它预告了接下来会发生什么，避免用户以为对话结束了。

4.4.4　最终答复卡（FinalAnswer）与溯源角标（RefChip）

角标状态视觉行为
可解析蓝色小角标可点击，跳转/高亮对应记录

答复末尾自动附一行脚注：「已核实 N 处引用」，若存在不可解析项则补充「存疑 M 处」。

resolveRef 的解析方式是按固定顺序在权限范围内查表（订单 → 采购单 → 产品 → 客户 → 商机 → 应收），而不是靠前缀猜类型。这一点重要：前缀猜测在标识格式变化时会静默失效，查表法则会诚实地返回「找不到」——而找不到正是我们要显示给用户的信息。

审计更正：这个功能是已实现的

仓库内 docs/agent-design.md §4 把「无法解析的引用标红划掉」列为最大的未实现缺口。该说法已过时——RefChip.tsx:21-30 已完整实现红色删除线，FinalAnswer 也已实现已核实/存疑计数。见 §9.2 审计项 A-06。

这类「文档比代码悲观」的漂移和「文档比代码乐观」的漂移一样有害：它会让接手的人去重复实现一个已经存在的功能。

4.5　Agent 话术规范

话术规范是 AI 产品经理特有的交付物——传统产品里文案是静态的，可以逐条评审；Agent 的输出是生成的，只能靠规则约束 + 评测抽查来保证。以下规则已写入 Executor 的 system prompt。

规则要求理由
R-2a只允许使用 6 类引用标记，且被引用的值必须逐字出现在工具结果里杜绝「看起来像引用其实是编的」——这是幻觉最隐蔽的形态
R-4a存在越界数据时必须披露；禁止使用「全公司只有 N 个」这类把切片当全局的表述用户会基于这句话做全局判断，而他看到的只是自己的切片
R-5涉及写入的步骤必须真的执行，不许用文字描述代替防止模型说「我已经帮你创建了采购单」而实际什么都没做
R-8区分「归因」与「预测」：数据支持的说成事实，推测的必须标明是推测企业场景里两者的责任归属完全不同
R-9与业务无关的问题礼貌引导回来，不发挥降低越界风险，也降低无意义的 token 消耗

Planner 侧另有一条容易被忽略但很重要的约束：禁止在给用户的文案里出现「工具」「函数」「接口」「场景」「录播」等词。原因是这些词会让用户意识到自己在跟一个「被编排好的系统」对话，从而降低对结论的信任；计划应该用业务语言描述（「查询 SKU-203 当前库存」而不是「调用 check_inventory 工具」）。

降级话术

模型失败后的重试卡文案是固定的：「左侧的客户、商机、订单、库存、应收数据不依赖模型，现在就能查。」

这句话的写法值得说明：它没有道歉（「抱歉，服务暂时不可用」），而是直接告诉用户下一步能干什么。失败时用户需要的是出路，不是致歉。

ADR-8 的那句「不能反过来」是这一册里最小的一条设计约束，也是最能说明问题的一条

结论文本里同时存在两套标记：模型写的 Markdown（**加粗**、- 列表）和我们自己定义的溯源标记 [[SO-2026-0412]]。两者都要解析，先后顺序却不是等价的——

先做 Markdown 再切引用，**[[SO-2026-0412]]** 会被加粗规则从中间劈开，一个可点击的溯源角标碎成两截文本；先切引用再对剩下的非引用段做行内解析，两者互不干扰。渲染顺序在这里等价于「排版好看」和「溯源可用」二选一，而溯源是这个产品全部可信度的落点，所以顺序被写死并加了注释。

之所以值得写进 ADR：这类约束不会体现在任何需求文档里，只在实现时出现一次，改错了也不报错——只是角标不再可点。它是「PM 是否真的读过自己产品的代码」的一个可验证样本。

ADR-6 里藏着一个真实的安全细节

会话按角色隔离不只是体验设计。如果不隔离，销售角色的历史会被带进 CEO 会话的 system prompt——反过来更糟，CEO 会话里查到的全公司数据会作为历史进入销售角色的下一轮提问。历史上下文是一条绕过 RBAC 的旁路，因为它不经过任何 scope 过滤。

代码里的处理是：会话按 userId 分桶，且 shouldRecordTurn 会丢弃那些「提问时是 A 角色、回答时已切到 B 角色」的回合。后者是一个只有真正实现过才会遇到的边界情况。

第 5 章　AI 方案落地性评估

这一章回答「能不能落地」。做法是先建一个可打分的判据框架，用它把系统里 18 个原子任务逐个分流，再看技术、成本、风险三条线，最后给出一张成熟度评分卡——诚实地说明现在距离生产可用还差什么。

5.1　评估框架：五维判据与打分规则

「这个任务该不该交给大模型」不能靠感觉。本册用五个维度打分，每维 1~5 分：

维度问什么1 分（不适合模型）5 分（适合模型）
D1 确定性这件事有唯一正确答案吗？有，且可由规则精确计算没有，依赖语境与表达
D2 错误可检出性如果做错了，用户能发现吗？发现不了（错误看起来很正常）一眼就能看出
D3 错误代价做错一次的后果多大？不可逆 / 涉及资金或承诺可逆 / 仅影响体验
D4 输入模糊度输入是结构化的还是自然语言？完全结构化自然语言、含指代与省略
D5 长尾程度需求是可枚举的还是长尾的？可枚举，做几个页面就覆盖了长尾，无法预先定义

判定规则

总分归属处理方式
≥ 18模型主导交给 LLM，代码只做校验
12 ~ 17模型 + 代码兜底LLM 产出，代码强制校验或人工确认
≤ 11代码主导写成确定性函数，模型只负责调用与转述

为什么设「一票否决」这条规则

因为 D2 和 D3 相乘才是真实风险。一个错了但看得出来的高代价操作是可控的（用户会拦下来）；一个错了看不出来的高代价操作是灾难——它会被当成正确答案一路传导到决策里。

本项目的交期风险计算正是这个组合：算错了后果严重（错误的交付承诺），而且算错了完全看不出来（模型会输出一段格式工整、语气笃定的错误分析）。所以无论它在 D4/D5 上得分多高，都必须落到代码里。这条规则把「凭直觉觉得该写死」变成了可复用的判据。

这张表的分界线其实非常干净

18 个任务的分界不在「难/易」，而在「有没有唯一正确答案」。

模型拿到的 7 项，没有一项存在标准答案——「这个问题该拆成几步」有很多种合理拆法，「怎么讲给用户听」也没有唯一写法。代码拿到的 10 项，每一项都有且只有一个正确结果——缺口就是 48 台，不多不少。

把有标准答案的事交给概率模型，是在用不确定性去解决一个本来确定的问题。这是我在这个项目里最核心的一条判断，也是第 2 章断点归因、第 3 章工具边界、第 6 章指标设计共同的底层依据。

这条分界带来的一个可验证的推论

如果分工正确，那么更换模型不应该影响任何数值结果——因为数值全部来自代码。本项目在开发过程中确实做了一次模型更换（GLM-4.5-Flash → qwen-plus），并跑了 9 个场景的能力边界回归已实测 n=9：数值结论完全一致，变化的只有表达风格与延迟。

这是一次意料之外的架构验证：模型可替换性本身就是分工正确的证据。如果换模型导致缺口从 48 变成了 50，那说明有计算漏到了模型侧。

① 引用可解析率 129/129。这是五道幻觉防线的直接验证——答复里每一个 [[编号]]，点下去都真的能落到一条用户可见的记录上。但见下方对 n 的说明，这个 100% 不能直接当成 100%。

② 输入 token 是输出的 10~30 倍，且随工具调用轮数超线性增长。最贵的一条（36,535 输入 / 6 个工具）与最便宜的多跳只读（6,972 / 3 个工具）差 5 倍，差的全部是每一轮重发的工具结果 JSON。已实测这条证实了 §5.5 的成本模型：优化成本的着力点在工具粒度和结果投影，不在压缩提示词。

③ 坏消息：P90 约 31s，未达 ≤ 30s 的目标。拖尾的是 edge-1（60.1s，14 个工具）——一个模型答不了、于是自行降级成穷举明细查询的归因类问题。能力边界之外的问题不是「答不好」，是「又慢又贵地答不好」，这比答不好更值得处理。对应措施见 §7.7 的单会话工具调用次数硬上限。

④ 坏消息：边界识别不稳定。edge-2（权限边界）2.7s、0 工具、空计划直接引导，处理得完全正确；edge-1（能力边界）却走了 14 个工具。两类边界的识别质量差距很大——权限边界是代码判定的（工具压根不在列表里），能力边界是模型判定的。这恰好是 §5.1 「有唯一正确答案的事不要交给模型」在数据上的一次印证。

关于这个 100%：n 到底是多少

129 条引用不是 129 个独立样本。它们来自 14 个场景，同一场景内的引用共享同一次工具调用结果、同一份上下文——如果一次调用取错了数据，那一整批引用会一起错。把 129 当独立样本量代入置信区间，会得到一个虚高的把握度。

诚实的报法是两个都给：按引用计 n=129，Wilson 95% CI = [97.1%, 100%]；按场景计 n=14（14/14 全部零死链），Wilson 95% CI = [78.5%, 100%]。后者才是这次测量真正支撑的结论——它说明「引用机制大体可用」，不足以说明「引用可解析率 ≥ 98%」。

要把下界抬到 98% 以上，按 §6.7.1 的算法需要约 190 个独立场景全部通过。这就是 §6.5 把评测集扩到 60 条、并要求分层覆盖的直接理由——不是为了显得严谨，是因为 14 条在数学上不够。

① 标注不会错。人工标注 60 条含多步计算的答案，出错率不会低——而评测集里的错误比模型的错误更有害，它会让正确的模型被判为错误。

6.7　统计功效：30 条能得出什么结论、不能得出什么

这一节回答一个很少被问、但决定评测有没有意义的问题：跑出来的差异，能不能证明不是运气？

6.7.1　单次测量的置信区间

假设在评测集上测得准确率 90%，不同样本量下的 95% Wilson 置信区间：

样本量 n观测准确率95% 置信区间区间宽度
3027/30 = 90%[74.4%, 96.5%]约 22 个百分点
6054/60 = 90%[79.9%, 95.3%]约 15 个百分点
200180/200 = 90%[85.1%, 93.4%]约 8 个百分点
30 条评测集的真实含义

如果用 30 条测出 90%，真实准确率可能低到 74%。也就是说，「我们的准确率是 90%」这句话在 n=30 时基本没有信息量——它与「准确率 75%」在统计上无法区分。

这就是本册把评测集从 30 条扩到 60 条的理由。但也要说清楚：60 条把下界从 74% 抬到 80%，仍然不能支撑「达到 90%」这种精确声明。60 条能支撑的结论是「不低于 80%」，这已经足够做上线判断（§6.8 的门槛因此设为 ≥ 85% 而非 ≥ 90%，并要求报区间而非点估计）。要真正声称 90%，需要 200 条以上。

6.7.2　对比实验所需的样本量

假设要检测「准确率从 80% 提升到 90%」这个幅度（α=0.05，功效 80%）：

设计所需样本量说明
独立两组（非配对）每组约 200 条共 400 次评测。题目难度的随机差异是主要噪声源
配对 + McNemar约 110 条同一批题跑两次。假设不一致对占比约 16%，需约 18 个不一致对
60 条配对功效不足预计仅约 10 个不一致对，无法达到 80% 功效
从这两行数字得出的三条实操结论

① 一律用配对设计。同样的结论，配对只需要 110 条而非 400 条——评测成本直接降到四分之一。而配对唯一的要求是「同一批题在两个配置下各跑一次」，几乎没有额外代价。这是评测设计里性价比最高的一个决定。

② 60 条的定位是回归门禁，不是效果论证。它跑得起（每次提交都跑）、能捕捉明显崩坏，但不足以支撑「新版本比旧版本好 10%」这类结论。想论证提升，必须扩到 110 条以上并做 McNemar 检验。两套用途，两种规模，不要混用。

③ 报告区间，不报点估计。本册所有目标值都应写成「≥ 下界」而非「= 某值」。一份写着「准确率 90%」的报告和一份写着「90%，95% CI [80%, 95%]，n=60」的报告，后者才是可被追问、可被复核的。

第 11 项（埋点）是所有非阻塞项的前置条件。第 8、9 两项写着「非阻塞」，但它们非阻塞的原因是「现在根本测不了」——不是因为不重要。埋点不上线，L2 全层和 L1 的一半指标都是纸面上的定义。

这两项的共同点很有意思：它们都不产出任何用户可见的功能，因此在排期里永远排在最后，然后被砍掉。把它们写进阻塞项，是产品经理少数几件必须硬扛的事之一。

7.2　评测进 CI：把质量变成门禁

一份不会自动运行的评测集，会在三次迭代之内失效。建议的三层门禁：

触发时机跑什么耗时预算失败后果
每次提交308 条单元测试（不调模型）秒级阻断合并
每次提交仅 Planner 的工具选择评测，60 条约 1~2 分钟阻断合并

定价模式适配性关键风险

7.10　人机责任边界：建议错了算谁的

这是企业 AI 产品必须在上线前书面回答的问题，也是最常被回避的一个。本项目的立场：

场景责任归属产品设计上的支撑
读操作：Agent 给的分析有误，用户据此决策用户前提是产品必须提供核对手段——这正是 [[ref]] 溯源角标与工具调用卡可见的责任设计意义。没有提供核对手段的系统，无权把责任推给用户
写操作：Agent 提议、用户批准、结果错误用户前提是确认卡显示的必须是真实即将发生的事（原则 P3）。G-01 未修复时，这个责任划分在那 3 个工具上不成立——用户批准的是模型的转述
写操作：未经确认就执行系统不应发生；Guard B + HITL 拦截
越权数据泄漏系统三层 RBAC；用户无从判断自己看到的是否越权
Agent 未发现风险（漏报）共担产品不承诺「发现全部风险」，只承诺「按规则推演窗口内的订单」。这个边界必须写进产品说明，而不是只写在设计文档里
这张表的内在逻辑：责任归属由产品设计决定，不是由免责声明决定

看前两行的「前提是」——责任能不能划给用户，取决于产品有没有给他判断的能力。一个不提供溯源的系统，说「结果仅供参考，请自行核实」是无效的，因为用户根本无从核实。

反过来说，本项目在溯源角标、工具调用可见、确认摘要查库这三件事上的投入，不只是可信度设计，同时也是责任边界的设计。它们让「用户应当自行判断」这句话变得成立。

这也是为什么 G-01 被评为 P0：它不只是一个功能缺口，它让第二行的责任划分在另外 2 个写工具上失去依据。

9.3.2　B-07 详解：实测数据是真的，但它的证据不在仓库里

agent-design.md §6 写着一句很有分量的话：「面试里任何一个数字都会被追问『你怎么测的』，所以这里不放估算值。」这个态度是对的，数据也确实是真跑出来的——端到端回归装置（e2e/regression.test.ts）真实调用线上 qwen-plus，逐条记录墙钟、token、工具链和引用核对结果。

问题在于最后一步：装置的输出通过环境变量 E2E_OUT 指定路径，实际写到了一个临时目录，没有任何一份被归档进仓库。

当前状态后果
文档里有数字读者只能选择相信
仓库里有装置读者可以重跑，但重跑得到的是新数字，不是复核旧数字——模型非确定，两次跑不一样（B-09 实测 2.6×）
仓库里没有原始输出文档中的每一个实测数字都无法被验证，也无法被差分比较。临时目录一旦清理，证据永久消失
为什么这条比「数字写错了」更严重

一个写错的数字是可以被发现和修正的；一个无法验证的正确数字，和一个无法验证的错误数字，在读者那里是同一样东西。

更具体地说，这条缺口直接摧毁了三件事：① §6.8 的上线门槛无法判定（门槛要对比历史值，没有历史值就没有对比）；② B-08 那种「两次运行的数字混在一套文档里」的问题无法被自动发现；③ 任何一次改动之后，「这次比上次慢了还是快了」这个最基本的问题答不上来。

修复成本极低——把 e2e-final.md 这类输出连同运行时间戳、模型名、代码 commit 一起归档进 docs/eval-runs/，一次提交的事。成本低而后果重，是所有缺口里最该先修的那一类。

9.4　根因分析与制度性修复

9.4.1　漂移的四个来源

来源典型症状对应条目
① 语义修订未回写某次提交调整了权限语义（给 CEO 开放写工具并加越权提示），代码改了，PRD 没改B-01 ~ B-03
② 技术替换未回写换模型、删功能，代码改了，设计文档与演示脚本没改B-04、B-12
③ 局部修正制造新矛盾发现某处数字错了，只改了看到的那一处，同一文档其余四处不动B-05、B-11
④ 证据与结论分离结论进了文档，产生结论的原始数据留在一次性目录里B-07、B-08、B-09

第 ③ 类和第 ④ 类是这次审计相对上一次的新增，也是更值得写下来的两类：

③ 说明「修文档」本身也是一种可能制造缺陷的操作。一份全错的文档至少是一致的，读者读完会得到一个统一（虽然错误）的认知；一份改对了五分之一的文档，读者会在内部矛盾处停下来，然后不知道该信哪一半。修文档的正确粒度是「一个事实的全部出现位置」，不是「我刚好看到的那一行」——这也正是 §9.4.2 主张自动生成的直接理由。

④ 说明可信度的载体不是结论，是证据。B-09 尤其能说明问题：跑间方差的数据已经跑出来了，只是没被汇总回文档，于是文档里仍写着「未统计」。做过的工作因为没有归档而等同于没做——这比没做更可惜，因为成本已经付了。

9.4.2　制度性修复：让文档不再需要靠人记得去改

措施解决说明
权限矩阵自动生成①③写一个脚本从各工具的 allowedRoles 直接生成 §3.3.1 那张表，作为构建产物。B-01~B-03 与 B-05 从此不可能再发生——12 项里消灭 4 项，且是永久消灭。投入产出比最高的一项
评测运行归档入库④每次端到端回归的原始输出连同时间戳、模型名、代码 commit 一起提交到 docs/eval-runs/。文档中的实测数字标注「取自 eval-runs/2026-09-02-1912.md」。B-07、B-08 一次性解决，并让 §6.8 的门槛第一次真的可判定
测试状态由 CI 徽章生成②README 不再手写测试数。人写的质量声明会过期，机器生成的不会。本次审计验证了两次：手写的「185 条全绿」先错了整整一天；改对之后三小时内又错了两次（B-13：同一文件里并存「236 用例」与「205 tests」，实际 308）。一个需要人记得去改的数字，修好它只是把下一次过期推迟几小时
确定性测试与非确定性测试物理隔离兜底已在审计窗口内自发完成（§9.3.1）。制度化的说法是：凡是需要外网、需要付费、结果不确定的检查，一律不进 npm test，另起配置与另起门禁
文档事实标注出处①②③凡引用配置常量的地方标注 文件:行号，使核对成本降到一次跳转。本册全篇如此
PR 模板加一栏「受影响文档」①②③低成本高效果。改 allowedRoles、改模型、删功能时强制勾选
修文档以「事实」为单位，不以「行」为单位③发现一个数字错了，先全仓库 grep 这个数字的所有出现位置，一次改完。B-05 就是没做这一步的直接产物
这一章真正想说明的事

12 项冲突里，没有一项是因为写文档的人不认真——恰恰相反，审计窗口内有人正在积极地修文档，四项冲突当场被消灭。它们全都是因为代码在演进而文档是静态快照，这是所有项目的默认结局，不是例外。

所以修复的重点不在「以后要记得更新文档」（这条规则从来没有生效过），而在把可自动生成的部分自动化，把不能自动化的部分标注来源，把产生结论的证据和结论放在一起。§9.4.2 的前两行——权限矩阵自动生成、评测运行归档入库——就能消灭这次审计 12 项里的 6 项。

这也是本册全篇标注 文件:行号、并对每个数字标注四级来源的原因：标了出处的陈述会随代码一起腐烂，但它的腐烂是可检测的——任何人跳转过去一看就知道对不对。没标出处的陈述则会静默地错下去，而且它错的时候看起来和对的时候一模一样。
