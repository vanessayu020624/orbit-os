第 3 章　产品需求文档（PRD）

本章是全册的规格主体。所有权限、工具、参数均以代码为准，与仓库内既有 docs/PRD.md 的差异已在第 9 章逐条列明。功能需求带验收标准，缺口登记册如实列出已知不足。

3.1　产品定位与设计原则

一句话定位：OrbitOS 是一个打通 CRM 与 ERP 数据的企业运营 Agent —— 它在每个员工自己的权限边界内，把跨系统的交叉核对压缩成一句话，并在结论之后允许直接执行处置动作，但每一次写入都必须由人确认。

五条设计原则

原则含义在代码中的体现
P1　模型只做判断，代码只做规则凡是能用确定性代码算准的（金额、缺口、日期差、风险等级），一律不交给模型risk.ts 全部数值计算为纯函数；confirmSummary 现查数据库；模型的输出里不应出现它自己算出来的数
P2　每个数字必须可核对回答中的实体标识必须是用户能在 UI 里翻到的那一个present.ts 投影层：只暴露业务单号（SO-2026-0412 / SKU-203），不暴露内部主键（SO-001 / P-003）；[[ref]] 角标可点击定位
P3　写操作必须由人拍板Agent 可以准备一个动作，但不能替人做决定4 个写工具全部 HITL 拦截；确认摘要由代码生成（§2.5）
P4　边界要说出来，不能装作没有看不到的数据要告知存在，而不是当作不存在scope.hidden 披露；Executor 规则 4a 明令禁止「全公司只有 N 个」这类表述
P5　AI 挂了系统还得能用Agent 是增量能力，不是承重墙5 个数据页面完全不经过 Agent；失败卡后紧跟「不依赖模型的数据现在就能查」

3.2　目标与非目标

本版本要做的本版本明确不做的
  • 四角色权限隔离的对话式查询（读）
  • 跨 CRM/ERP 的交叉推演（交期风险）
  • 写操作的 HITL 确认与审计留痕
  • 数字可溯源（[[ref]] 角标 + 无法解析时标红）
  • 不依赖模型的 5 个数据页面 + 仪表盘
  • 会话按角色隔离、可归档
  • 不做真实 ERP/CRM 对接——数据为固定种子生成，目的是可复现与可回归
  • 不做主动推送——风险需用户提问才触发（缺口 G-03）
  • 不做跨会话长期记忆——单会话内最近 6 轮原文 + 更早轮次折叠成 300 字摘要，会话之外不留存
  • 不做模型微调——全部能力来自 prompt + 工具设计
  • 不做移动端
  • 不做多租户——单公司单实例
这个参数被定错过一次，值得单独讲

最初的值是最近 2 轮，理由写得很像回事：企业数据问答的典型会话是 1~3 轮，长程记忆收益低；而历史要同时进 Planner 和 Executor 的 system prompt，token 成本近似线性增长，旧数据还会与新结果冲突诱发幻觉。

这套推理唯一的问题是：它假设的会话形状不是真实的会话形状。真实的追问链是「查风险 → 看某张订单 → 问这个客户的应收 → 回头说『用方案 1』」——到第四问时第一问已经掉出窗口，模型会把「方案 1」理解成刚才那个客户的事。2 轮够接住紧邻指代，接不住跨话题回指。

现值是 HISTORY_TURNS = 6 原文 + 更早轮次滚动折叠成 SUMMARY_MAX = 300 字摘要（summarize.ts）。不无限往上加的原因仍然是成本：Executor 的 system prompt 本身就带工具目录，历史每多一轮都要乘进后面每一次 function calling 的往返。

可迁移的一点：上下文窗口大小不是一个可以拍脑袋定的常数，它取决于「用户的指代最远指向多久之前」。这个距离只能靠观测得到，所以 §6.3 的「会话轮次分布」埋点不是锦上添花——它是这个参数唯一的校准依据。

供应链角色的权限设计是本产品最见功力的一处

王强能看到全部 160 张订单但金额被遮蔽，能看到全部 48 个客户但看不到任何商机和应收。这个组合不是随手配的，它精确对应一句业务判断：供应链需要知道「要发什么货给谁、什么时候」，但不需要知道「这单赚多少钱」。

如果按常见做法「供应链只能看跟他有关的订单」，那 simulate_delivery_risk 就永远算不准——因为库存台账的推演必须覆盖窗口内全部待发货订单，少一张结果就是错的。权限的粒度必须服从业务计算的完整性要求，而不是反过来。这是从第 2 章断点③ 直接推导出来的设计。

3.3.3　显式拒绝对（DENIED_PAIRS）

代码中显式声明了 5 组「角色 × 数据域」的拒绝关系代码事实（rbac.ts:123-129）：销售/总监 × 采购单，销售/供应链 × 应收，供应链 × 商机。侧边栏对应导航项显示为灰色 + 挂锁图标，但仍可点击——点进去是一个说明为什么无权的页面，而不是直接消失。

这个选择是刻意的：菜单项直接消失会让用户以为「系统没这个功能」，从而去别处找；显示但锁定则传达「有这个功能，但不是你的职权范围」。前者制造困惑，后者传达组织边界。

3.5.2　工具边界的三条判据

判据说明正例 / 反例
① 一个工具 = 一个业务问题不做「万能查询工具」，因为参数空间越大模型填错的概率越高正例：simulate_delivery_risk 直接回答「哪些单会晚」；反例：如果只给 query_orders + check_inventory，模型必须自己做台账推演——而它一定会算错
② 计算留在代码，不留给模型凡涉及数值推演的，封装成工具而非让模型多次调用后自行汇总aggregate_metrics 返回聚合结果而非明细；模型拿到的就是最终数
③ 写操作粒度对齐审批单元写工具的粒度必须等于用户一次点「批准」愿意承担的责任范围正例：create_purchase_order 一次一单；反例：批量下单工具——用户无法对一个批次做出有意义的确认
最能说明判据 ① 的一个例子：simulate_delivery_risk 为什么必须存在

假设不提供这个工具，模型要回答「哪几单会晚」必须：查库存拿到 42 → 查订单拿到三张单及各自数量与承诺日 → 按日期排序 → 逐单扣减台账 → 比对在途 PO 的 ETA → 判定风险等级。加粗部分是纯计算，而语言模型做多步算术的可靠性众所周知。

更糟的是这类错误看起来完全正常——它会输出一个格式正确、语气笃定、数字错误的答案。而这恰恰是企业场景里最危险的失败模式。

所以：凡是「规则明确、多步推演、错了不易被发现」的计算，一律封装成工具。模型的职责缩减为「判断此刻该调这个工具」和「把结果讲成人话」——这两件事它做得比人好，而算术它做得比代码差。

3.5.3　工具描述即产品文案

工具的 description 字段是模型选择工具的唯一依据，因此它是写给模型看的产品文档，需要按产品文案的标准打磨。本项目的三条约定：

  • 写清楚「什么时候用」而不只是「这是什么」——例如 simulate_delivery_risk 的描述强调「当需要判断现有订单能否按承诺交期交付时使用」，而不是「模拟交付风险」。
  • 写清楚返回什么——让模型能预判是否需要再调其它工具，减少无效轮次。
  • 默认值写进描述——这一条目前没做好：多数工具的 limit 默认值 ?? 20 写在代码里、不在 schema 描述中，模型不知道自己不传 limit 会得到 20 条。登记为 G-04。

版本规划里最容易被跳过、但最不该跳过的一条

V2 的准出条件写的是「真实数据下 L1 指标不低于模拟数据下的 90%」，而不是「接入完成」。

原因：本项目全部指标都建立在固定种子生成的数据上——数据干净、字段完整、无脏值、无歧义命名。真实 ERP 里同一个客户可能有三个名字、订单状态字段可能有历史遗留的枚举值、库存表可能有负数。模拟数据上的高准确率不能外推到真实数据。

把这个衰减幅度设为 V2 的准出门槛，等于承认「接入真实数据是一次会掉分的迁移」，并提前给出可接受的掉分幅度。这比接完再发现问题要好得多。
