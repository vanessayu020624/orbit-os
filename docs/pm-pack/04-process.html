#断在哪直接现象代价
①权限断层：销售无库存表访问权必须找人代查，或凭印象承诺每次查询引入一次人工往返；忙时直接跳过这步

2.2　断点归因：为什么这五处必然断

五个断点不是执行不力，是流程结构的必然产物。归因如下：

断点结构性原因为什么加强管理解决不了该由谁解决
①权限按组织职能划分，而问题按业务链路发生放开权限会引入数据泄露风险（销售能看到全公司库存与成本）；不放开就必须人工中转代码：三层 RBAC 在角色边界内提供只读投影（§2.6）
②ERP 的 available 字段语义是「当前未被占用」，不含「未来将被占用」这是数据模型语义问题，培训改不了字段含义代码：simulateDeliveryRisk 按承诺交期升序推演台账（纯函数、确定性）
③承诺动作发生在三个人的三个时刻，无串行化点要求「承诺前先报备」等于给每单加一道审批，销售会绕开代码：同上，推演天然覆盖全部待发货订单
④阈值告警是存量模型，风险是流量问题调低安全库存阈值只会制造大量误报代码：风险分级用 ETA 与承诺日期之差，不用阈值
⑤没有人被指派在「承诺之后、到期之前」这个窗口做检查指派了也没人做——这活的收益归公司，成本归个人（§1.2）模型：把检查的触发成本降到问一句话
归因得出的分工原则

看最后一列：五个断点里四个该由代码解决，只有一个该由模型解决。这不是保守，是准确——①~④ 都是「规则明确、只是没人执行」，把明确的规则交给概率模型是自找麻烦；⑤ 是「规则明确但不知道何时该执行」，这才是语言模型的位置。

模型的价值在于降低触发成本与表达成本，不在于计算。这条原则在第 5 章会被扩展成 18 个任务的逐个判定，并且在代码里已经落实：所有数值计算都在工具的 TypeScript 里完成，模型只负责选工具、填参数、把结果讲成人话。

为什么是 Planner–Executor 两段式，而不是纯 ReAct

纯 ReAct（想一步做一步）在企业场景有两个具体问题：① 用户在第一秒看不到 Agent 打算干什么，只能盯着转圈；② 无法在执行前判断本次是否涉及写操作，HITL 的准备工作没有着力点。

两段式的代价是多一次 LLM 调用（首字延迟增加），换来的是：计划先行渲染给用户（可预期）、needsWrite 在执行前已知（可预防）、以及计划本身成为一个可评测的中间产物——工具选择准确率能在不跑完整链路的情况下单独回归（§6.2）。第三点是评测体系能成立的前提，这是选择两段式最实际的理由。

补偿设计：Executor 允许在执行中发现计划不足时追加步骤（plan_amended 事件，正则 /需要追加步骤[：:]\s*(.+)/ 提取），保留了 ReAct 的适应性。

HITL 设计中最关键的一条：确认摘要由代码生成

确认卡上写的「向锐驰机电采购 48 台，单价 12,320 元，总计 591,360 元，预计 9 月 9 日到货」——这些数字不是模型写的，是 confirmSummary(args, db) 现查数据库算的。

理由很直接：如果摘要由模型生成，那么用户点「批准」时批准的是模型的转述，而实际执行的是 args。两者一旦不一致——模型说 48 台、args 里是 480 台——用户的确认就是无效的，而 HITL 的全部意义就在这一次确认上。确认界面必须显示即将真实发生的事，而不是对它的描述。

已知不足：这条原则目前只有 create_purchase_order 完整做到（查库算成本与 ETA）。create_followup_task 和 reserve_inventory 的摘要是纯参数回显、零查库。这是一处真实缺口，登记为 G-01（§3.7）。

审计发现：第 3 层有一处实现不一致

rbac.ts:79 定义了 maskOrderForRole，但没有任何工具调用它——订单金额的实际遮蔽发生在 present.ts 的另一份实现里。功能上没有漏洞（遮蔽确实生效了），但存在两份并行的遮蔽逻辑，后续任一处修改都可能造成分歧。登记为审计项 A-08（§9.2）。

另一处：写路径的 scope 校验覆盖率是 1/4——4 个写工具里只有 update_order_promise_date 调用了 scopeOrders。也就是说，理论上销售可以对不属于自己的客户创建跟进任务。当前不构成实际漏洞（工具参数由模型从 scope 过的读结果中取得），但这是一条依赖上游的隐式约束，登记为 G-02（§3.7）。

2.7　异常与降级流程

2.7.1　模型不调用工具时的三道兜底

最常见的失败模式不是模型调错工具，而是模型不调工具、直接用常识编一段话。代码里有三道针对性防线代码事实：

兜底触发条件动作触发上限
Guard A
loop.ts:118		本轮无 tool_calls 且 toolResults == 0 且用户未拒绝过回灌一条催促消息，要求先调工具再作答仅一次；第二次直接中止
写入催促
loop.ts:134		计划里有写步骤，但模型准备收尾时还没执行过任何写工具回灌提醒「尚未执行的写入步骤」仅一次
Guard C
loop.ts:153		最终答复里出现无法在工具结果中解析的 [[ref]]给一次改写机会（refined 标记），要求去掉编造的引用仅一次

为什么每道都只给一次机会：无限重试在成本上不可接受（每次都是一整轮 LLM 调用），在体验上更糟（用户面对无限转圈）。给一次机会 + 失败即降级为诚实的错误提示，是成本、体验、正确性三者的平衡点。这个「只补推一次」的约束在测试里有专门用例覆盖——loop.test.ts 中断言 Guard A 只触发一次、Guard C 只重写一次的那几条，正是审计窗口内被修复的那批（§9.3.1）。

2.7.2　模型调用失败的降级

describeLlmError 把底层异常分成五类，各自给不同的用户话术代码事实（llm.ts:145-162）：

类别判定用户看到的
超时45 秒未返回提示模型响应超时，建议重试或简化问题
限流HTTP 429已自动退避重试 3 次（1.5s / 4s / 9s）仍失败，提示稍后再试
服务端错误5xx；401/403 单独识别401/403 明确提示密钥问题，不让用户误以为是自己的操作问题
网络fetch 抛错提示网络不通
未知兜底原始信息 + 通用建议
降级的产品设计：失败卡后面永远跟一张「你现在能干什么」

任何一类失败发生后，UI 都会在错误卡之后追加一张重试卡，文案是：「左侧的客户、商机、订单、库存、应收数据不依赖模型，现在就能查。」

这句话是本产品降级策略的浓缩：AI 是增量能力，不是系统的承重墙。模型挂了，OrbitOS 退化成一个普通的 CRM/ERP 前端，用户该查的还能查。一个把核心业务流程架在模型可用性上的设计，在企业环境里是不可接受的——这也是为什么全部 5 个数据页面都不经过 Agent 独立可用（§4.1）。

2.7.3　用户拒绝写操作后的流程

拒绝不是终止。userDeclined = true 后有三个连锁效果代码事实：① 跳过 executeTool 与审计留痕（拒绝的操作不该进审计流水）；② 向模型回灌明确指令「请据此调整建议，不要重复尝试」——防止模型换个参数再试一次这种令人恼火的行为；③ 关闭 Guard A（既然用户主动拒绝了，此后模型不调工具就直接收尾，不再催促）。

第三点值得单独说：拒绝之后模型不调工具是合理的，因为它已经无路可走，此时应该做的是解释和给替代方案，而不是被系统逼着再调一次工具。把「用户拒绝」这个信号正确传导到后续所有分支，是 HITL 从「一个弹窗」变成「一条完整流程」的分界线。
