第 8 章　Skills：能力面与能力模型

「Skills」在这个项目里有两重含义：Agent 的能力面——它会什么、不会什么、怎么扩展；以及AI 产品负责人的能力模型——这个项目验证了哪些能力，用什么证据验证的。本章两者都写。

「明确不具备的能力」为什么要写进能力地图

因为 Agent 产品的能力边界对用户是不可见的。传统软件里，没有的功能就没有按钮，用户一看便知；Agent 只有一个输入框，用户会假设它什么都能干，然后在失败时得出「这东西不行」的结论。

把边界显式写出来有两个用处：对内，它是工具扩展的排期依据（每一条都是一个候选需求）；对外，它是产品说明和引导文案的来源——与其让用户试错发现边界，不如直接告诉他。这与 §7.10 最后一行「产品不承诺发现全部风险，这个边界必须写进产品说明」是同一件事。

8.2　能力扩展路线与准入判据

8.2.1　新工具准入的四道判据

判据问题不通过则
J1它回答的是一个完整的业务问题，还是一个数据查询片段？片段类的应合并进已有工具，否则会推高工具调用次数（成本超线性，§5.5）
J2它内部的计算是否全部确定性？若需模型参与计算，回到 §5.1 打分；D2/D3 双低则一票否决
J3它的权限边界能否用现有 allowedRoles + scope* 表达？不能表达说明权限模型需要先扩展，工具要等
J4如果是写工具：确认摘要能否完全由数据库算出？不能则不允许上线（这正是 G-01 的教训）

最核心		能判断哪些任务该交给模型、哪些绝不能，并说得出判据§5.1 五维框架 + §5.2 的 18 任务判定表；结论「10 项归代码、7 项归模型」，分界线是「有没有唯一正确答案」（§5.3）

S6 成本意识知道成本从哪来、能反推设计识别出成本随工具调用次数超线性增长（§5.5），并反推出「工具粒度设计同时是成本设计」

S8 边界的自觉说得出「什么情况下不该用我的产品」§1.4 承认 BI 看板与定时脚本在各自场景中更优，并给出三条适用边界
如果只能保留一项，是 S1

因为 S2 到 S8 全都是 S1 的下游：

正因为判定「计算归代码」，评测集的标准答案才能由代码自动生成（S4）；正因为数值不在模型侧，换模型才能不改变任何结论（§5.3 的意外验证）；正因为确认摘要归代码，HITL 才是真的（S5）；正因为工具要一次回答一个完整业务问题，成本才可控（S6）。

「哪些活交给模型」这一个判断，决定了后面所有事情的难度。判断对了，评测、成本、可信度都会变简单；判断错了，后面每一项都要用更复杂的手段去补救一个本可以避免的问题。

8.4　可迁移方法论卡片

以下六条是从本项目中提炼、可直接用在其它 Agent 项目上的判断，每条都附本项目的具体出处。

#方法论出处与说明
M1有唯一正确答案的事，不要交给概率模型。分界不在难易，在于「是否存在标准答案」§5.3。推论：架构分工正确时，换模型不应改变任何数值结论——这是一条可执行的自检
M2错误代价高 × 错误难发现 = 一票否决。两者相乘才是真实风险§5.1。一个错了看得出来的高危操作是可控的；错了看不出来的才是灾难
M3确认界面必须显示即将真实发生的事，而不是对它的描述。§2.5 / ADR-2。摘要由模型生成时，用户批准的是转述，HITL 形同虚设
M4Agent 系统里，模型是不可信主体。它发起的每次调用都要像外部请求一样鉴权§7.4.2。可见性过滤是体验优化，执行复检才是安全边界，两者不可互相替代
M5工具粒度同时是正确性设计、性能设计和成本设计。§3.5.2 + §5.5。一个工具回答一个完整业务问题，同时改善了三件事——这是 Agent 产品里罕见的三赢点
M6报区间，不报点估计；用配对，不用独立组。§6.7。n=30 测出 90% 意味着真实值可能只有 74%；配对设计能把评测成本降到四分之一
还有一条不在表里的

能写出自己产品的缺点清单，比能写出优点清单更难，也更有用。

本册第 3.7 节列了 11 个缺口，第 9 章列了 12 项文档冲突，包括 B-07 与 B-08 这两条直接指向本册自身可信度的问题——本册引用的全部实测数字，其原始输出文件不在仓库里，且分别来自两次不同的运行。这些内容不会让交付物看起来更漂亮，但它们是这份文档唯一能证明「其余部分是可信的」的方式——一份没有缺点的评估报告，读者只能选择相信或不信；一份主动列出缺点的报告，读者可以验证。
