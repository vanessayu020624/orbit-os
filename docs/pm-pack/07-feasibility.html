第 5 章　AI 方案落地性评估

这一章回答「能不能落地」。做法是先建一个可打分的判据框架，用它把系统里 18 个原子任务逐个分流，再看技术、成本、风险三条线，最后给出一张成熟度评分卡——诚实地说明现在距离生产可用还差什么。

5.1　评估框架：五维判据与打分规则

「这个任务该不该交给大模型」不能靠感觉。本册用五个维度打分，每维 1~5 分：

维度问什么1 分（不适合模型）5 分（适合模型）
D1 确定性这件事有唯一正确答案吗？有，且可由规则精确计算没有，依赖语境与表达
D2 错误可检出性如果做错了，用户能发现吗？发现不了（错误看起来很正常）一眼就能看出
D3 错误代价做错一次的后果多大？不可逆 / 涉及资金或承诺可逆 / 仅影响体验
D4 输入模糊度输入是结构化的还是自然语言？完全结构化自然语言、含指代与省略
D5 长尾程度需求是可枚举的还是长尾的？可枚举，做几个页面就覆盖了长尾，无法预先定义

判定规则

总分归属处理方式
≥ 18模型主导交给 LLM，代码只做校验
12 ~ 17模型 + 代码兜底LLM 产出，代码强制校验或人工确认
≤ 11代码主导写成确定性函数，模型只负责调用与转述
一票否决：D3 ≤ 2（错误代价高）且 D2 ≤ 2（错误难发现）→ 无论总分多少，一律降为代码主导或强制 HITL
为什么设「一票否决」这条规则

因为 D2 和 D3 相乘才是真实风险。一个错了但看得出来的高代价操作是可控的（用户会拦下来）；一个错了看不出来的高代价操作是灾难——它会被当成正确答案一路传导到决策里。

本项目的交期风险计算正是这个组合：算错了后果严重（错误的交付承诺），而且算错了完全看不出来（模型会输出一段格式工整、语气笃定的错误分析）。所以无论它在 D4/D5 上得分多高，都必须落到代码里。这条规则把「凭直觉觉得该写死」变成了可复用的判据。

5.3　判定结果与「模型只做判断、代码只做规则」

归属任务数共同特征
模型主导7全部是理解、组织、表达类：把模糊的输入变清晰，把结构化的输出变自然
模型 + 代码兜底1参数填写——处在交界处，因此用 schema 约束 + HITL 双保险
代码主导10全部是计算、判定、留痕类：有唯一正确答案，错了不易被发现
这张表的分界线其实非常干净

18 个任务的分界不在「难/易」，而在「有没有唯一正确答案」。

模型拿到的 7 项，没有一项存在标准答案——「这个问题该拆成几步」有很多种合理拆法，「怎么讲给用户听」也没有唯一写法。代码拿到的 10 项，每一项都有且只有一个正确结果——缺口就是 48 台，不多不少。

把有标准答案的事交给概率模型，是在用不确定性去解决一个本来确定的问题。这是我在这个项目里最核心的一条判断，也是第 2 章断点归因、第 3 章工具边界、第 6 章指标设计共同的底层依据。

这条分界带来的一个可验证的推论

如果分工正确，那么更换模型不应该影响任何数值结果——因为数值全部来自代码。本项目在开发过程中确实做了一次模型更换（GLM-4.5-Flash → qwen-plus），并跑了 9 个场景的能力边界回归已实测 n=9：数值结论完全一致，变化的只有表达风格与延迟。

这是一次意料之外的架构验证：模型可替换性本身就是分工正确的证据。如果换模型导致缺口从 48 变成了 50，那说明有计算漏到了模型侧。

真实 ERP 数据下准确率不会崩Demo 好看、上线报废V2 准出条件：真实数据下 L1 不低于模拟数据的 90%（§3.8）
第四条赌注最值得单独讲

「用户会认真读确认卡」是所有 HITL 设计共同的隐含假设，也是最少被检验的一条。现实是：如果 Agent 的建议 20 次里有 19 次是对的，人就会开始闭眼点批准。此时 HITL 在流程图上还在，在实质上已经消失了。

这意味着 HITL 不能只当作安全兜底，它需要被持续监测：确认卡停留时长如果收敛到 1 秒以内、拒绝率如果连续数周为 0，说明这道防线已经名存实亡，应当反过来减少弹卡频率（只对高风险操作弹）来恢复它的信号强度。一个从不被拒绝的确认，等价于没有确认。

5.5　成本模型与单位经济性（敏感性矩阵）

我不知道当前 API 的实际单价，因此这一节不给绝对金额，只给参数化公式与敏感矩阵。这与 §1.5 是同一处理原则。

这一节的相对系数现在有实测锚点了

本节的敏感性矩阵原本全部是推演。已实测的 14 条端到端回归（§6.2.1）给出了真实分布：单会话总 token 中位 9,024，区间 1,404 ~ 37,605，倍差 26.8×。

这个倍差验证了下面矩阵的核心判断：成本的方差几乎全部来自工具调用次数。最便宜的一次（edge-2，1,404 token）只有 Planner 一次调用、0 次工具；最贵的一次（ceo-3，37,605 token / 26 个事件）在一轮会话里连续取数并下了一张加急采购单。输入 token 占总量的 94.4%（172,311 / 182,501），与「主要成本项是 Executor 的输入」这一结论一致。

但矩阵里的具体系数（2.5×、7×、1.3×）仍是推演，未被逐项验证——要验证它们需要控制变量地重跑同一问题并只改一个参数，这属于 §6.6 的对照实验设计，尚未执行。

5.5.1　单次会话的 token 构成

单次会话 token
  = Planner 输入（system + 工具清单 + 历史 + 问题）
  + Planner 输出（计划 JSON，jsonMode 下通常很短）
  + Σ Executor 输入（system + 计划 + 工具 schema + 累积的工具结果）   ← 主要成本
  + Σ Executor 输出（tool_calls 或最终答复）

主要成本项是 Executor 的输入：每多调一次工具，之前所有工具结果都要
随下一轮请求再发一遍 —— 成本随工具调用次数二次增长，不是线性。

5.5.3　敏感性矩阵：单次会话成本对什么最敏感

设单次会话的相对成本为 1.0（基准：2 次工具调用、无历史）。变动各参数后的相对成本：

变动相对成本说明
基准（2 次工具调用）1.00—

工具调用 2 → 8 次约 7×接近 MAX_TURNS 一半时成本已失控
带 6 轮历史 + 摘要约 1.3×Planner 与 Executor 各带一份；折叠使其不随会话长度继续增长

CEO 角色（15 工具 schema）vs 销售（9 个）约 1.15×影响小于预期，因 schema 只占输入一小部分

相对倍数由 token 构成公式推算，非实测。绝对值需按 §7.7 的埋点上线后测量。

这张表最重要的一行是第二行

工具调用次数是成本的第一驱动因素，而且是超线性的。这直接反推出一条产品设计原则：与其优化 prompt 长度，不如减少工具调用次数。

而减少调用次数最有效的手段，恰恰是 §3.5.2 的判据 ①——一个工具直接回答一个业务问题。simulate_delivery_risk 把原本需要 3~5 次调用才能凑出的推演压缩成 1 次，它同时改善了三件事：正确性（不让模型算术）、延迟、以及成本。

这是本项目里少见的「三赢」设计点。值得记下的方法论是：在 Agent 产品里，工具粒度的设计同时是正确性设计、性能设计和成本设计。

Go / No-Go 结论

结论：架构 Go，上线 No-Go。

Go 的部分：模型/代码的分工判断已被验证（换模型数值不变），权限与可信度的核心机制已实现，架构上没有需要推倒重来的地方。这是最贵的部分，它已经过关了。

No-Go 的部分：三块短板都在「知道自己做得怎么样」这一层——没有埋点（不知道线上表现）、没跑评测（不知道模型准确率）、测试红着（不知道改动有没有破坏功能）。这三件事的共同点是：它们不增加任何功能，但没有它们就无法判断系统是否在正常工作。

上线前必须做的三件事，按顺序：① 把实测原始输出归档入库、每场景重复 5~10 次并进 CI（B-07、G-11、§6.7.3）；② 埋点上线，让 L1/L2 指标可计算（§7.1）；③ 补齐 G-01/G-02 两个 P0/P1 缺口。做完这三件，成熟度可达 4.0，具备灰度上线条件。
