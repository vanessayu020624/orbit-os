第 6 章　量化指标与对比方法

这一章是本册的重心。「量化」不难，难的是三件事：指标要能真的被算出来（有埋点）、要能归因（分层）、以及比出来的差异要能证明不是噪声。最后一件是绝大多数 AI 产品评估文档缺失的部分，本章 §6.7 专门处理。

6.1　三层指标体系总表

L3 业务层 这套系统有没有让公司少赔钱 周期：月 / 季 ──────────────────────────────────────────────────────────────── 交期违约率 ↓ 风险发现提前量 ↑ 人工跨部门核对次数 ↓ ▲ │ 受什么驱动？ │ L2 产品层 用户是不是真的在用、用得顺不顺 周期：周 ──────────────────────────────────────────────────────────────── 周活跃提问用户 任务完成率 追问率 确认卡拒绝率 降级触发率 ▲ │ 受什么驱动？ │ L1 模型层 模型本身干得对不对 周期：每次提交 / 每日 ──────────────────────────────────────────────────────────────── 工具选择准确率 参数正确率 引用可解析率 越界披露正确率 无据编造率 空结果诚实率 端到端耗时 单会话 token 自下而上的因果链：L1 决定 L2 的上限，L2 决定 L3 能否发生。 自上而下的排查链：L3 没动 → 查 L2 是不是没人用 → 查 L1 是不是答得不对。
为什么必须分三层，不能只报一个「准确率」

只报一个总准确率，出问题时无法归因。举个具体的例子：假设线上发现「交期违约率没下降」（L3 没动），可能的原因至少有三类——模型答错了（L1 问题）、模型答对了但没人问（L2 问题）、都对但业务流程没跟着改（L3 之外的组织问题）。三者的解法完全不同：第一个要改 prompt 和工具，第二个要改入口和推送，第三个要改的是人的工作方式。

分层的价值就是让「指标没动」这件事变成一个可以逐层下钻的问题，而不是一个只能拍脑袋讨论的问题。

为什么把「工具选择准确率」放在第一位

因为它是最上游、最便宜、最能预警的指标，三个性质同时成立：

最上游——工具选错，后面全错，且错得毫无挽回余地。答案的所有质量问题里，工具选错是唯一一个下游无法补救的。

最便宜——它只需要跑 Planner 一次，不需要执行工具、不需要生成最终答复。评测一条的成本大约是完整链路的 1/5，所以它可以跑得很频繁（每次提交都跑）。这正是选择 Planner–Executor 两段式架构的实际回报（§2.4 ADR-1）：中间产物可单独评测，是评测体系能进 CI 的前提。

最能预警——改 prompt、换模型、加工具，任何一个动作都会先在这个指标上反映出来。它是整个评测体系的金丝雀。

① 引用可解析率 129/129。这是五道幻觉防线的直接验证——答复里每一个 [[编号]]，点下去都真的能落到一条用户可见的记录上。但见下方对 n 的说明，这个 100% 不能直接当成 100%。

② 输入 token 是输出的 10~30 倍，且随工具调用轮数超线性增长。最贵的一条（36,535 输入 / 6 个工具）与最便宜的多跳只读（6,972 / 3 个工具）差 5 倍，差的全部是每一轮重发的工具结果 JSON。已实测这条证实了 §5.5 的成本模型：优化成本的着力点在工具粒度和结果投影，不在压缩提示词。

③ 坏消息：P90 约 31s，未达 ≤ 30s 的目标。拖尾的是 edge-1（60.1s，14 个工具）——一个模型答不了、于是自行降级成穷举明细查询的归因类问题。能力边界之外的问题不是「答不好」，是「又慢又贵地答不好」，这比答不好更值得处理。对应措施见 §7.7 的单会话工具调用次数硬上限。

④ 坏消息：边界识别不稳定。edge-2（权限边界）2.7s、0 工具、空计划直接引导，处理得完全正确；edge-1（能力边界）却走了 14 个工具。两类边界的识别质量差距很大——权限边界是代码判定的（工具压根不在列表里），能力边界是模型判定的。这恰好是 §5.1 「有唯一正确答案的事不要交给模型」在数据上的一次印证。

关于这个 100%：n 到底是多少

129 条引用不是 129 个独立样本。它们来自 14 个场景，同一场景内的引用共享同一次工具调用结果、同一份上下文——如果一次调用取错了数据，那一整批引用会一起错。把 129 当独立样本量代入置信区间，会得到一个虚高的把握度。

诚实的报法是两个都给：按引用计 n=129，Wilson 95% CI = [97.1%, 100%]；按场景计 n=14（14/14 全部零死链），Wilson 95% CI = [78.5%, 100%]。后者才是这次测量真正支撑的结论——它说明「引用机制大体可用」，不足以说明「引用可解析率 ≥ 98%」。

要把下界抬到 98% 以上，按 §6.7.1 的算法需要约 190 个独立场景全部通过。这就是 §6.5 把评测集扩到 60 条、并要求分层覆盖的直接理由——不是为了显得严谨，是因为 14 条在数学上不够。

确认卡拒绝率：一个双向阈值指标

这是本册唯一一个设了下限的指标。常规思路是「拒绝率越低说明 Agent 建议越准」，但在 HITL 场景下这个推理是错的：

  • 拒绝率 > 15%：Agent 的建议质量有问题，用户在频繁纠正它 → 查 L1
  • 拒绝率 < 2%：更值得警惕。要么 Agent 完美（不可能），要么用户已经不看了。结合「停留时长中位数 < 2s」即可确认是后者

确认为后者时的处置不是去教育用户认真看，而是收窄弹卡范围——只对高金额、不可逆的操作弹确认，低风险操作改为事后可撤销。让每一次弹窗都值得被认真对待，比让用户面对大量弹窗更有效。

评测集设计的一条硬要求：标准答案必须由代码生成

C1/C2 的标准答案（缺口 48 台、2 张高风险单）不是人工填的，是调用 simulateDeliveryRisk 等纯函数算出来的。这带来两个好处：

① 标注不会错。人工标注 60 条含多步计算的答案，出错率不会低——而评测集里的错误比模型的错误更有害，它会让正确的模型被判为错误。

② 数据变了标准答案自动跟着变。如果哪天调整了种子或埋雷场景，标准答案自动重算，评测集不会腐烂。

这一点之所以可行，恰恰是因为 §5.2 的分工——所有数值都在代码里，所以代码天然就是 ground truth 的生产者。如果计算散落在模型侧，这个评测集根本没法自动化。正确的架构分工会在评测阶段第二次付给你回报。

6.6　怎么对比：五组对照实验设计

用户明确要求「如何对比」。有指标不等于能对比——对比的关键是把「跟谁比、控制什么、看什么差异」说清楚。以下五组实验按优先级排列。

实验组 A　人工基线测量（必须最先做）

对比对象人工跨系统核对　vs　Agent 问答
方法影子测试：给 8~10 名真实员工同一组任务（如「确认这三张单能否按期交」），秒表计时并记录跨部门询问次数、最终结论是否正确
控制同一批任务、同一数据快照；顺序随机（一半人先人工、一半先 Agent），消除学习效应
看什么单任务耗时、跨部门询问次数、结论正确率
为什么必须先做没有基线，所有「提升 X%」的说法都是空的。而这个基线一旦上线就再也测不到了——用户用过 Agent 之后，他的「人工方式」已经被污染

实验组 B　方案对比：Agent vs 看板 vs 脚本

对比对象Agent　vs　预定义 BI 看板　vs　定时脚本推送（即 §1.4 的方案 B、F）
方法准备两组任务：Q1 常规问题（看板已覆盖的，如「本月营收」）、Q2 长尾问题（看板未覆盖的，如「这三张单里该先保哪张」）。三种方案各跑一遍
看什么可回答率、耗时、正确率，分 Q1 / Q2 两组分别报告
预期结论Q1 上看板应当胜出（更快更稳），Q2 上只有 Agent 能答。这个实验的目的不是证明 Agent 更好，而是划清它的适用边界——如果 Q1 上 Agent 也胜出，说明看板做得不好，不能算 Agent 的功劳

实验组 C　有无 Agent 的漏检对比（价值论证的关键实验）

对比对象不用 Agent 的对照组　vs　用 Agent 的实验组
方法构造 N 组订单场景，其中一部分埋有交期风险（比例对参与者保密）。两组参与者各自判断「哪些单会晚」
看什么净增检出率 Δ = 实验组检出率 − 对照组检出率
为什么关键Δ 是 §1.5 价值公式里唯一未知的关键参数。整份商业论证的成败押在这一个数上——它 ≥ 10% 则项目成立，< 5% 则应重新考虑是否该用方案 F（定时脚本）代替

6.7　统计功效：30 条能得出什么结论、不能得出什么

这一节回答一个很少被问、但决定评测有没有意义的问题：跑出来的差异，能不能证明不是运气？

6.7.1　单次测量的置信区间

假设在评测集上测得准确率 90%，不同样本量下的 95% Wilson 置信区间：

样本量 n观测准确率95% 置信区间区间宽度
3027/30 = 90%[74.4%, 96.5%]约 22 个百分点
6054/60 = 90%[79.9%, 95.3%]约 15 个百分点
200180/200 = 90%[85.1%, 93.4%]约 8 个百分点
30 条评测集的真实含义

如果用 30 条测出 90%，真实准确率可能低到 74%。也就是说，「我们的准确率是 90%」这句话在 n=30 时基本没有信息量——它与「准确率 75%」在统计上无法区分。

这就是本册把评测集从 30 条扩到 60 条的理由。但也要说清楚：60 条把下界从 74% 抬到 80%，仍然不能支撑「达到 90%」这种精确声明。60 条能支撑的结论是「不低于 80%」，这已经足够做上线判断（§6.8 的门槛因此设为 ≥ 85% 而非 ≥ 90%，并要求报区间而非点估计）。要真正声称 90%，需要 200 条以上。

从这两行数字得出的三条实操结论

① 一律用配对设计。同样的结论，配对只需要 110 条而非 400 条——评测成本直接降到四分之一。而配对唯一的要求是「同一批题在两个配置下各跑一次」，几乎没有额外代价。这是评测设计里性价比最高的一个决定。

② 60 条的定位是回归门禁，不是效果论证。它跑得起（每次提交都跑）、能捕捉明显崩坏，但不足以支撑「新版本比旧版本好 10%」这类结论。想论证提升，必须扩到 110 条以上并做 McNemar 检验。两套用途，两种规模，不要混用。

③ 报告区间，不报点估计。本册所有目标值都应写成「≥ 下界」而非「= 某值」。一份写着「准确率 90%」的报告和一份写着「90%，95% CI [80%, 95%]，n=60」的报告，后者才是可被追问、可被复核的。

6.7.3　跑间方差：为什么「跑一遍」不能作为门槛判据

上面两节讨论的是题目带来的抽样误差。还有一个更容易被忽略的噪声源：同一道题、同一个配置、跑两遍，结果也不一样。模型是非确定的，工具链、耗时、token 全都会变。

这一项在设计文档里被记为「未统计」，但数据其实已经存在——回归装置在调试期间对同一场景重复跑过多次已实测：

推翻的第一个：「跑间方差未统计」。数据早就跑出来了，只是没被汇总回文档——见 §9.2 的 B-09。做过而没归档的工作，在读者那里等同于没做，而成本已经付了。

推翻的第二个：§6.2.1 那张实测表可以直接当基线。不能。既然同一场景的耗时能在 24s 和 62s 之间摆动，那么「P90 约 31s」这个数字本身就带着一个宽得多的不确定区间。拿单次观测去卡一个 30s 的门槛，本质上是在测量噪声。

还能读出一条设计信息：方差大小与「路径是否确定」强相关。rep-2 只有一条合理路径，方差来自措辞长短；edge-1 没有正确路径，模型每次编排出不同的降级方案，工具数在 4 到 14 之间跳。方差可以当作「这个问题是否在能力边界内」的一个客观信号——不需要人来判断，跑五遍看离散度即可。这比让模型自我评估「我能不能答」可靠得多。

由此得出的门槛修正：凡是涉及耗时、token、准确率的阈值判定，必须基于每场景重复 5~10 次的中位数与 P90，而不是单次值。这条写进了 §6.8 的第 14 项。

这张表里最容易被跳过的两项：第 10 和第 11

第 10 项（人工基线）是唯一一个「过期作废」的门槛。其它任何一项都可以上线后再补，唯独人工基线不行——一旦用户用过 Agent，他的人工工作方式就已经改变，那个基线永远消失了。而没有基线，这个项目将永远无法证明自己创造了价值。它排在第 10 位，但应该第一个做。

第 11 项（埋点）是所有非阻塞项的前置条件。第 8、9 两项写着「非阻塞」，但它们非阻塞的原因是「现在根本测不了」——不是因为不重要。埋点不上线，L2 全层和 L1 的一半指标都是纸面上的定义。

这两项的共同点很有意思：它们都不产出任何用户可见的功能，因此在排期里永远排在最后，然后被砍掉。把它们写进阻塞项，是产品经理少数几件必须硬扛的事之一。
